# FOM 基岩原生资源覆盖与维护

2026-10-21，全量排查与第一批适配已发布。范围是现役 FOM 2.42 / Minecraft 1.21.1 / NeoForge 21.1.250；不更换整合包、不重建世界。当前生产入口见 [接入与运维说明](MY-AGENT-WORLD-FOM-BEDROCK.md)，实际上线及验证范围见 [发布证据](evidence/fom-bedrock-blocks-20261021.json)。

从实际注册表逐项统计，区分物品、世界方块状态、实体类型和专用渲染器。原版替代物、可找到源模型、扩展成功加载，都不能单独算作画面已适配。

54,113 个状态中，23,880 个不带方块实体；其余当前只覆盖静态底座，机器内部、库存物品、活动部件等专用渲染仍需独立适配。这不是全部模组或 Java 与基岩像素一致的验收。

动画已覆盖经验块、超级经验块、部分风扇催化剂、固体燃烧器、余烬符文和末影抽屉等。基岩原生支持动画、模型控制器、粒子和声音；机械转速、食物烹饪进度等还需要接真实游戏状态。它们的剩余缺口在本服的转换及状态同步链路，不能解释成基岩不支持动态效果。

## 数据链路

1. 网关在原版显示映射前保存原始模组状态，连接私有频道 `mawbedrock:blocks` 携带状态。
2. Geyser 扩展在协议解码后、默认区块翻译前恢复独立虚拟 Java 状态；使用公开自定义方块 API 关联对应基岩几何、材质、碰撞和灯光字段。
3. 全量区块、单块更新、批量更新走同一张表；重连重新提供全量状态。观察器握手后补发保留的数据，不触发挖掘、放置等动作。
4. 普通世界方块不使用显示实体，不占用或重写原版方块编号。游戏逻辑仍由 NeoForge 原方块执行。

帧格式为 `MWB1`、类型、递增序号、原文长度和原始 Deflate。限制单帧压缩后 1 MiB、原文 2 MiB；解析验证长度、位置、状态白名单和顺序。类型 1 是区块中的原生单元，类型 2 是绝对坐标更新；原始区块光照、群系和其他字段保留。

三维方块物品只接受原物品模型与对应世界变体的几何、UV、图集一致、且 GUI 姿态符合当前支持条件的条目。由基岩使用该方块模型生成图标，避免裁一张正面图充当三维物品。原始物品堆栈、组件和客户端库存哈希在连接内双向还原；虚拟物品必须先被本连接观察到。最新 Geyser 的非原版物品定义还需要补齐关联方块运行时编号，扩展对支持的三个协议表在初始化后完成关联。

## 明确剩余的适配任务

| 类别 | 当前处理与下一步 |
| --- | --- |
| 机械转动、装配结构、载具 | 静态底座不代表运动完成；按真实转速、轴向、应力、装配实体状态同步，停止时必须停止动画 |
| 灶台、篝火、切菜板食物 | 静态方块与食物层分开；需接实际物品、槽位及烹饪进度，移走食物后清除显示 |
| OBJ、独立／组合渲染器、精妙背包 | 当前不能按普通 JSON 方块模型自动转换，保留具体 loader 和源资源缺口 |
| UV 锁定、位置加权随机、染色、位置偏移 | 当前不猜测旋转、变体或颜色；须补原算法／客户端实际烘焙数据及对照验证 |
| 高于一格或超过 16 个碰撞盒的方块 | 当前固定 Geyser 组件校验有明确限制，未截断或夹紧成错误碰撞；需专门处理扩展碰撞 |
| 资源优先级冲突 | 不凭 JAR 字典顺序选择；需要原客户端实际生效的资源栈证据 |
| 模组生物、NPC、武器动作、专用 GUI | 分别接实体模型、装备层、动作和界面状态；图标或方块成功不代表这些已完成 |

逐项清单保存在私有 `E:\MC\research\fom-full-visuals-20261021\audit-final-v9` 的 items / blocks / states JSONL；候选中的 `native-block-coverage.json` 按方块列出已覆盖状态数和剩余原因。`tools/fom_bedrock_audit.py` 可对任意同格式候选或正式发布重跑，`allContentAdapted` 始终按实际验收保守报告。

## 构建与验证

- `tools/build_fom_support.py --neoforge 21.1.250` 构建只读导出能力；在隔离且注册表匹配的服务端执行 OP4 `maw_registry visuals`，生成原始碰撞、选择盒和物理数据。正式游戏 JAR 本批不更换。
- `tools/fom_bedrock_blocks.py --compile` 用固定 Geyser / ViaProxy JAR、Java 21 编译扩展；Geyser SHA 必须匹配。
- 同工具 `--assets … --states … --shapes … --extension … --output …` 转换世界方块；`--block-items --input … --items … --idmap … --projection … --output …` 在新目录增加严格匹配的三维方块物品。
- `tools/prepare_fom_bedrock.py --output … --install-blocks …` 只向未启动的研究候选安装资源，校验真实状态表、物品投影和 Geyser 构建。
- 生成需要带 Pillow 的构建 Python；正式运行和健康验证仅用独立标准库 Python。原 PNG、模型、JAR、原始包、玩家数据和世界均不提交 Git。

隔离导出实例只有一个只读诊断 Support JAR 与正式不同。全部 186,696 个状态的编号、名称、属性及非几何字段相同；遮挡盒有 40 个双精度数值出现最高约 5.55e-17 差异，转 float32 后全部一致。原始文件 SHA 不相同的失败记录保留，没有把它改报成逐字节一致。

验证包括 51 项 Python、29 项相关 Node 回归和固定 Geyser 的 18 项真实编解码 JVM 断言；原先更广的 41 项 Node 组合也通过。真实 UDP 世界方块检查 13 项、三维物品及女仆／75 秒会话 21 项、同身份库存恢复 10 项、最终放置与清理 23 项均通过。基岩实际放下安山机壳后，原生独立查询确认 `create:andesite_casing`，数量只减少一个；随后换槽仍保留原身份，临时方块和物品分别经原生查询确认清理。

协议客户端每 10 秒做一次本人私有只读查询维持测试活动，75 秒样本不代表真人无输入挂机或多玩家压力测试。手机 GPU 的最终材质、动画和手柄画面仍需要真实客户端验收。早期放置探针使用了过期的服务端方向物品编码，被 Geyser 正常拒绝；按固定协议分开编码装备与交易描述符后通过，未放宽正式包校验。控制台回执只证明命令投递，测试必须等原生查询确认状态，不能把 `deliveryKnown` 当成执行成功。

维护守护会验证资源契约、文件哈希与漂移，并检查本次进程实际注册的方块、物品、运行时关联和下载包。启用方块包时基岩桥堆上限独立设为 2 GiB；隔离发现旧 512 MiB 不足，原失败日志保留。不会因此修改游戏服的 6 GiB 上限。未经隔离验收的渲染器不应靠关闭校验发布。

基岩动画的原生机制参考 [Microsoft：方块动画贴图](https://learn.microsoft.com/en-us/minecraft/creator/documents/createanimatedblocktexture?view=minecraft-bedrock-stable)，自定义方块接口参考 [Geyser 文档](https://geysermc.org/wiki/geyser/custom-blocks/)。上游 Rainbow / Hydraulic 当前分支面向更新游戏版本，本批没有直接装入本服。
