# 原生五人队伍与聊天联动候选

用户确认采用**原生五人队伍**。当前四只加入同一队伍即可，保留第五席；不创建额外角色，也不为了“满编”补人。队伍、邀请、接受、退队和队长继任全部沿用原生管理器，辅助入口只读状态并给出本人下一步，不保存另一份成员或邀请账本。文档路径及既有四人验收入口保持兼容。

本轮在社交候选上补齐四个现有角色共同组队的协作入口，并额外验证五人完整入队。没有连接生产游戏、改四个宿主的配置、代任何角色建队/接受邀请、重启服务或发布包。

## 复用的队伍

实际游戏队伍沿用 Vortex 的 `ExpeditionPartyManager`。本轮核对的[上游源码](https://github.com/Sauron05/vortexrpg/blob/main/src/main/java/io/vortexcore/world/ExpeditionPartyManager.java)上限为五人，四人无需再造名册或把六组双人 Party 拼起来。原 `world/sidecar/party_*` 的 survivor/maid 主人、会话和身体绑定仍是双人兼容接口，不能拿它冒充四个外部玩家。

新入口：

```text
/mycli guild party plan <发起者> <伙伴1> <伙伴2> <伙伴3> --json
```

四个角色使用**同一份有序名单**，名单包含本人，名字从当次真实在线玩家复制。入口支持二到五人的计划，四人为主要验收目标；这是预期结伴名单，实际容量与变更仍由原生管理器执行。原生 `create/invite/accept/leave/disband` 不改语义、权限或状态。

`plan` 只读原生队伍和有效邀请，返回**调用者本人的**下一步，不自动执行，不另存队伍、邀请或模型任务。已有队伍就复用；只有尚无可复用队伍时由名单首位发起。四人不应分别创建四个队伍。

| 状态 | 本人下一步 |
| --- | --- |
| 尚未建队，自己是发起者 | 选择一次 `create`，核对实际结果 |
| 尚未建队，自己是其余成员 | 等发起者建队和邀请 |
| 自己是原生队长，尚有缺员 | 一次只邀请下一位在线、尚未入队且没有有效邀请的成员 |
| 自己收到目标队伍有效邀请 | 自行选择 `accept`；不替其他角色接受 |
| 已发有效邀请 | 等接收者处理，不反复覆盖邀请 |
| 成员分属不同队伍或有其他队伍邀请 | 先协商；不自动退队、踢人、解散或转移队长 |
| 已有成员加上名单缺员超过五人 | 返回 `capacity_conflict`，先协商调整；不反复邀请或接受必定超员的队伍 |
| 目标不在线 | 保留原队伍，等待重连；不把缺席推断为已加入或已离队 |
| 四个目标 UUID 都在同一个原生队伍 | `membershipConfirmed=true`，再读 `status` 检查集合 |

`status` 增加原生 `partyId` 与 `selfUuid`，未入队时 `partyId=null/memberCount=0`。组队是否完成以四端读回的同一个真实 `partyId` 和成员 UUID 为准，邀请成功、聊天答应及本地配置都不算。原生队长离队后的继任沿原生逻辑，不另建队伍；服务器重启后仍需重查原生会话状态。

## 与四人聊天的关系

独立自治运行时现在把配置中的伙伴名字/UUID 和本人标记交给各自模型，同时明确它们**不是已入队证明**。模型按实际广告的帮助和工具读取多人组队计划、使用原生聊天动作提交真正的组队命令，继续沿原回合、回执和未知结果保护处理。没有额外自动组队进程、模型请求或聊天定时器。

收到 `nativeParty/partyPlan` 原生事实时，它们在紧张上下文中先于场景杂项保留，身体、队列、战斗能力和服务器失败反馈仍优先。实际服务端工具结果也继续沿原工具历史进入当前角色上下文；本次没有假造未接入适配器的事实。对没有加载本运行时或新版服务能力的宿主，仍须检查实际接入，不能把提示词更新说成四端已连通。

入队不证明已集合、听见聊天、完成分工或参与副本。跨世界的队员仍是成员，附近聊天继续按原服务器真实路由决定听众；没有接收事件就不补造“已听见”。`plan` 明确返回 `nearbyHearingVerified=false/activityParticipationVerified=false`。集合继续沿现有 `status` 和 `locate tp` 指引，既有费用、冷却与活动门禁保持。

## 已实际执行的离线验证

- `PartyFormationTest`：162 条确定性断言，覆盖四个调用者的建队/等待/邀请/接受/成队顺序、邀请冲突、不同队伍、离线、原生队长范围、重复身份、五人边界、已有非目标成员占用容量、只读及旧双人兼容。
- `NativeFourPartyTest`：76 条断言，使用真实上游管理器实现完成 **1 次创建＋3 次邀请＋3 位接收者本人接受**；四位读回同一个原生队伍 ID。另验第五人可加入、第六人被原生容量拒绝、退队、原生队长继任和重新入队复用原 ID。这里是原生 Java 类的离线运行，不是四个实服客户端或 LLM 验收。
- `NativeFivePartyTest`：106 条断言，完整验证 **1 次创建＋4 次邀请＋4 位接收者本人接受**、五端同一个原生队伍 ID、第六人拒绝；也明确验证当前四人可先成队并保留第五席，不把“容量五人”误作“必须凑齐五人”。三组 Java 离线测试合计 344 条断言通过。
- 2 项构建拒绝测试：错误基包不创建输出、不启动编译器、不改输入；旧冻结构建器不能把本次新源码打进旧候选名称。
- 2 项自治上下文测试：四人目标名单不伪装已入队；真实四人组队事实及其原始引用在场景杂项前保留。

本轮自治全量为 **1820 通过、28 条件跳过、1 失败**；唯一失败仍是此前已在原主干复现的锁定 `rc.145` 归档缺失，没有改锁或绕过校验。组队/社交/RPG上下文专项 **55 项通过**；本轮修改文件通过对应 Ruff 规则。重新构建并在源码目录外安装自治 wheel，验证实际收件、模型端口消费、四人名单与未知入队状态均通过，禁用真实网络/模型/进程调用。没有改核心包源码，未重复运行此前已通过的核心全量。
