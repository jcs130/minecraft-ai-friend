## 持续运行的故障边界

- 后台推理失败、无最终答复或原生循环保护结束的是本轮推理。控制器记录失败并指数退避，随后重新观察、开启新轮；不再因连续两次失败关闭人物。原有预算、并发和推理退避继续生效。
- QwenPaw 的后台 task 句柄存于进程内。只有原生接口准确返回该 task 的不存在错误，且同角色原生 tracker 确认 idle/0，才将丢失推理记为失败、释放本轮通道。保留 task、session、请求身份和未验证标记，不重投旧请求、不推断动作成功。普通代理 404、断网、忙碌及未知提交均不能这样释放。
- 临时网关和文件 IO 故障在原服务里退避，Docker `unless-stopped` 负责进程退出后的拉起。已知基础设施暂停只有在原生空闲、身体与动作所有权均明确时才恢复；人工暂停、维护 drain 和未知动作保持保护。
- 复用 QwenPaw 的 DriverManager、凭据解析、原生重连与熔断。2.2.1 的同值白名单 PUT 可能只刷新失效 handler 的元数据，因此增加限于游戏自有固定端点的兼容修复：同值 PUT 后仍无工具、角色空闲、卡片未变，才调用原生 `reload_driver`，每连接至少间隔 60 秒。GET 健康探针不产生重连写入；不通过完整 Client DTO 覆盖凭据。兼容入口校验已审阅版本和源码哈希，升级时须重新审阅。
- 结衣先验证原生身体与交流工具连接，再提交生活轮。无法连接时不消耗新模型请求；原有 Qwen Cron 信号、身份绑定和统一请求闸门继续使用。
- 服务管理器原先先等 Qwen 完整健康再启动 survivor，而完整健康又依赖 survivor MCP。现在先确认 Qwen 进程运行，启动后续身体服务，最后执行完整健康检查；最终检查失败仍保留失败回执，不能报告成功。其他服务的健康门槛保持。

## 系统 1：局部状态到候选动作

已连接本地开源复现 `Mapika/decider-2b`，接口 `/v1/systemone`，实际响应模型标识 `decider-dev`。这是用户已有的共享本地服务，不替换 QwenPaw 模型，也不经工具名称代理拼装参数。

技能 `next(state,memory)` 可返回 `choose:{question,candidates}`，候选为 2–8 个 `{id,description,action}`。完整参数由已测试程序依据当前事实构造；本地模型只选候选，null 动作为上交慢系统。正常的确定性程序继续零模型执行。新增契约仍走 draft → test → promote → start，fixtures 的 `expectedChoice` 测候选生成，离线测试不调用模型。

每次只传紧凑身体状态、短目标和上一动作结果，不传完整聊天、历史思考或累积轨迹。2 秒 HTTP 超时、5 秒观测新鲜度、0.75 置信门槛；非法输出、低置信度和服务故障均退回原 Qwen 规划器。现有动作租约、权限、原生回执、目标验证和未知结果不重放继续生效。

选择、状态哈希、模型标识、候选、概率和延迟写入原有轨迹，并用派发 turnId 关联动作回执，供后续 L2/RSI 实验取证。概率不是校准后的安全保证，选择成功不等于任务完成。这批数据尚不是清洗完的训练集，本轮没有训练或微调模型。

## 2026-09-21 实地验证

首版 `0850d88a…` 的 7 个 fixtures 通过，但实际装备候选缺少 `action:"equip"`。Decider 在 139 ms 内以 0.9839 置信度选中铁剑，网关返回 `invalid_equip`，没有执行身体动作。原实践记录保留为 replan、0 个确认动作；其验收同时要求进食与装备，而程序只执行一次动作，目标定义也不成立。fixture 比较生成值不能证明动作参数有效，模型高置信不能证明动作正确。操作者提供上述具体诊断，再由桐人通过同名 refinement 关联失败实践修订；这种有人工反馈的修订不能报告为完全自主 RSI。

## 2026-09-21 配置与局部感知优化

`compact_state` 沿用身体快照，无额外每步 RCON 查询，补充 `maxHp`、`saturation`、`air`、`biome`、六个装备位的有限字段及最多 32 种物品数量。候选参数 `item_id` 对应物品优先，未知库存为 null，超限/无效条目通过 `countsTruncated` 明示；不能把未展示的物品认定为不存在。位置、任务和上一条回执也只投影固定字段，原始 inventory/NBT、嵌套历史和思考不进入局部请求。8192 字节、5 秒新鲜度、原动作租约和未知结果禁止重放的边界保持；这仍是每次有界完整快照，不是增量 KV 会话。
