2026-10-15。基于 FOM 2.42 / Minecraft 1.21.1 / NeoForge 21.1.248。

不把第三方 JAR 提交到公共 Git。部分资源有非商业或保留权利许可；公开再分发前按各作者许可处理。

## Agent 最少需要知道的内容

先看 `/fom help`、`/fom status`、`/fom inventory`、`/fom nearby`；需要核对脚边方块时使用 `/fom inspect x y z`。只查询自己的状态，等待 `MC_AUTH_STATE` 明确授权后行动。更多内容从游戏里的配方书、模组手册和真实菜单学习。

完整模组客户端配合现有 MAW Client Bridge 0.5.0，可以读取物品/配方、操作原生界面、获取原始画面并执行普通输入。未增加另一套任务执行器，没有启动新的自主模型循环。

- **烹饪**：查看原生配方。烹饪锅需要实际热源、材料和容器；查询完成不等于食物已交付，核对输出和实际扣物。
- **女仆**：以原生交互完成认主，进入本人女仆的界面。模组会自动发放入门道具，初始化后其 ID 可以由 `smart_slab` 变为 `smart_slab_init`；应同时核对数量、主人组件和原生规则。
- **魔法**：在 **Inscription Table（铭文台）** 把卷轴写入法术书，再正常装备到 Curios 的法术书槽位。Arcane Anvil（奥术铁砧）不是这步操作使用的工作站。选择法术、瞄准并按原生施法键，服务端照常检查魔力和冷却。

对锁定的 Iron's Spells 版本，普通施法输入示例见 [fom-cast-equipped-spell.py](../examples/fom-cast-equipped-spell.py)，可由 `minescript.run` 执行。脚本返回只表示脚本执行结果，需要另查目标和实际资源变化。客户端魔力读数来自 `ClientMagicData.getPlayerMana()`；不能拿服务端 `MagicData` 对象读取本地玩家，否则可能错误地显示 0。

Minescript 的 Python 必须实际可用，不能指向 Windows Store 的占位解释器。部分后加载的模组按键不在其缓存的 `press_key_bind` 名单里；示例调用对应版本的原生按键对象，结束时释放输入。操作结果未知时保持账本原状，不自动重投。

## Mineflayer 翻译层的改动

沿用现有网关，新增 Farmer 的嵌套物品、烹饪时间、炒锅状态，以及 Iron 的法术容器、升级、地图、装备和 NBT 组件解码。所有组件 ID 从 **当前模组组合的实际导出** 查找，没有沿用原 96 个 JAR 的数字顺序。

法术书的容量、法术数、等级和槽位使用固定大端 INT。非法负数或过大数量先拒绝，避免读入后续物品。Farmer 的时间戳采用真正的 64 位 VarLong；锁定依赖的默认实现按 32 位读取，因此使用隔离的专用编解码器，保留高位和负数。

原版连接只收到可理解的物品投影；服务端原物品和组件不变。决策以 `/fom inventory` 的 `nativeId` 为准，不能据 `paper` 等基础投影类型判断物品身份。存取串行执行，等待容器、本人库存和光标确认后再继续。

女仆等原版无法渲染的实体仍按现有策略省略原版实体包，并保留私有兼容提示和 `/fom nearby` 的真实信息，不伪装成普通村民。复杂模组界面、女仆管理、原生施法和模型动画优先使用完整 Java 客户端。基础投影通过不代表普通 Mineflayer 已能执行全部模组玩法。

实测发现未适配的法术粒子会断开原版连接。现在只在明确启用的原版投影中略过无法解码的独立 `world_particles` 帧，私有提示每次连接一次。实测连续三次火焰粒子后连接和库存查询正常。必需物品/实体元数据、截断包和长度不符仍严格拒绝；完整 Java 客户端继续使用原生特效。

## 女仆的 Curios 兼容数据包

女仆 1.5.3 的通用实体配置引用了本包不存在的 `feet` 和 `scroll` 槽位，启动时新增两条 Curios ERROR。`world/fom-content-data` 覆盖同一资源，保留本组合已注册的 11 个通用槽位，且只在女仆和 Curios 都安装时生效。没有新增玩家装备栏、改动第三方 JAR 或屏蔽日志；后续更换模组组合要重新核对。

这是服务端数据包，放入 `world/datapacks/qdfom_content_compat`；客户端不单独安装它。

## 实际验收

隔离新平坦世界，普通非 OP QA，材料、生物和热源由明确的管理员夹具提供；本轮 0 模型调用。

- 实际合成铁厨刀，消耗 1 铁锭和 1 木棍；加热烹饪锅产出 2 份熟米饭，消耗 2 水稻和 2 碗，光标为空。
- 实际消耗 1 蛋糕认主女仆，原生主人界面可打开。服务端独立读回主人 UUID，重启后保持。
- 实际放置完整铭文台，写入火弹卷轴并装备法术书；正常施法命中尸壳，出现燃烧效果。客户端同步魔力 100→91，目标血量 12.096→6.1919994。数值包含自然回复及伤害规则，不能据此把法术固定消耗写成 9。
- 未修改的 Mineflayer 4.39 实际接入新组合，世界、认证、食物、厨刀、女仆背包、法术书和卷轴正常加载。六栈物品（含模组入门道具）存入普通箱子，关闭重开后取回；服务端核对五类夹具数量、空箱、空光标及卷轴/女仆组件，重连保持。
- 原生客户端画面已实际查看：烹饪锅、女仆界面、铭文台、法术书和火弹命中均来自真实渲染。
- 候选服正常退出并冷启动，食物、厨刀、法术书、法术数据和女仆主人保持。新配置由现有拥有者守护管理 Java 与网关，不增加无守护后台服务。
- 101 项 Node 协议/映射回归、25 项 Python 守护/增量包检查通过；健康探针覆盖原生连接、网关、认证策略、哈希和拥有者心跳。
- 正式服三分钟维护预告后确认无人在线，原拥有者正常停止；7,378 文件全服冷备（662,570,565 字节 ZIP）完成 CRC、每文件 SHA256 和双盘副本校验。原 96 个服务端及 124 个客户端 JAR 的哈希保持。
- 正式服重新导出注册表，原生 ID、名称及全部状态属性与已冻结网关一致。频道 JSON 的顺序独立核对；几何盒双精度最低位差异单独记录，最大差值约 5.55e-17，没有用容差接受不同的 ID 或属性。
- 正式原版 Mineflayer 6 项登录/区块/私有查询检查通过；完整模组客户端进入原有自然世界，实际读到三类物品目录（185 / 73 / 231 项）并取得真实帧。QA 正常退出，现役 FOM 的 9 项健康检查通过。
- 女仆槽位修正后，候选冷启动的新增独有 ERROR 为 0；原包已有的 311 类错误没有隐藏，不称整个整合包零错误。

首次脚本错误、过早连接和入门道具初始化导致的测试断言失败保留。Minescript 解释器失败产生的旧 unknown 只按实际审计解除后续操作限制，原动作仍为 unknown，没有改成成功或重复执行。

仍未验收：自然采集完整发展链、女仆自主种田、全部法术和自定义 GUI、多人航空器、16 Agent 长期负载。旧 Web 3D 和基岩桥尚未接入本 FOM 内容组合，不能据原生截图宣布它们已兼容。

## 准备增量包

把锁文件所列六个官方下载 JAR 放进单独目录，然后执行：

```powershell
python tools/prepare_fom_content.py --downloads E:\你的下载目录 --output E:\新的内容增量包目录
```

工具核对全部哈希与原生 mod ID，准备 `mods`、服务端数据包、锁文件和说明；文本数据包按 LF 规范化，支持 Windows 的 CRLF checkout。目标目录必须不存在；不会覆盖已安装游戏、修改玩家数据或自动部署。客户端和服务端都同步六个 JAR；服务端再安装兼容数据包。本机已更新的游戏目录是 `E:\MC\clients\fom-2.42\minecraft\versions\fom-2.42`；上层 `minecraft` 是资源和库缓存，不能把模组放错位置。

部署新增内容前要正常停服，完整冷备世界、认证库、原 mods、配置和运维发布清单到双盘；在全新目录冻结与实际注册表匹配的网关。普通客户端同步后再开放游戏入口。不要使用插件热加载或把候选平坦世界覆盖到正式世界。

正式服回退应先停服，恢复同一份冷备中的原 96 个 JAR、原网关、配置及**升级前世界**。新模组物品和方块进入世界后，单独删 JAR 会丢失内容；是否回退升级后的玩家进度需单独决定。候选服回退不触及正式 FOM 或 Paper。
