# 按需读取 Minecraft 玩法资料

游戏角色共用 `qd-minecraft-guide` 资料入口，每位角色的副本由 QwenPaw 原生 SkillService 管理。原生 Toolkit 常驻提示词只含技能名称、简介和目录；`Skill` 加载该技能的短正文；官方 `read_file` 再读取自身 `skills/qd-minecraft-guide/references/` 中与当前问题相关的一页。正文和参考资料不会由同步工具拼进 AGENTS.md，也不需要额外模型、向量库或常驻检索进程。

入口涵盖合成、装备成长、农耕、建造、交易与公会、游戏法术和女仆原生工作。不会要求每轮遍历全部资料。角色已有原生 make-skill 能以相同结构建立个人资料技能，把常驻简介、任务指引、参考数据分开；记忆只保留必要结论、来源、适用条件与后续目标。

实测发现桐人原本的本地 QPM4 会在第5次模型请求前等待超时，虽然资料已读完，却没有最终回答。按用户允许增加 CodingPlan 用量的要求，桐人调整为 QPM8，保留并发1、每任务6次迭代、180秒决策间隔和滚动24小时48次自主决策。Qwen2.2限流器按 provider:model 在进程内首次缓存，离线同步后需重启游戏Qwen才会实际更新；不重置用量账本，也不增加模型规划循环。

## 配方来源

桐人新增只读 `lookup_recipe(item_id)`，复用已安装 Numen 的原生查询，并从当前服务器 RecipeManager 获取配方。查询不需要动作租约，不执行合成，不改变背包或决策账本；实际制作继续由原 `craft` 或对应游戏设施执行，消耗真实材料。

原生查询支持标准合成、烹饪、切石和锻造类型，包括使用这些类型的模组配方。每次最多四条；当前原生结果缺少 recipeId，材料文本可能省略命名空间，也未覆盖全部自定义机器配方。因此“未查到”只表示此查询支持范围内没有匹配；不能据此断言物品不可制作，更不能凭简称猜材料 ID。来源和这些限制随结果返回。原生 `ingot(any)` 一类共同词缀会改写为“未展开候选组”，并显式返回 `ingredientsResolved:false`、`materialAvailability:not_checked`，防止把未枚举的替代集合误认为所有同类材料都合法。

例如要制作铁魔法的奥术锭：按需读取合成参考，查询 `irons_spellbooks:arcane_ingot`，再依据真实背包确认材料、数量、替代项和设施。只有当前角色具有身体动作工具且获得有效调度租约，才能进一步制作。村民策划或女仆阅读这份资料，不会获得桐人的身份和工具。

旧 Numen 的生存及建筑资料继续通过 `knowledge_catalog`、分页 `knowledge_read` 读取。它们明确标为历史参考，不将旧坐标、工具名或屠龙路线自动升级为当前目标。版本与模组内容变动后以当前世界查询为先。

## 同步与验证

`world/ops/sync_role_learning.py` 在游戏 Qwen 停止时使用原生服务安装完整技能包，备份既有正文和参考页。参考页更新先在临时工作区进行原生整包扫描，再写入受管目录，并通过原生 enable 再扫描实际目录；健康检查验证每一页与源码一致。独立注册女仆继承女仆模板的资料绑定，保留自身人格、模型、会话和预算。

`tools/smoke_progressive_knowledge.py` 使用离线临时 Qwen 容器验证“简介 → 正文 → 单页参考”的真实加载行为。`tools/game_knowledge_health.py` 已接入总健康检查，验证七个现有角色的参考页及原生 API、第43项配方工具。配方测试验证只读边界；实机查询和可选 `tools/exercise_minecraft_knowledge.py` CodingPlan 实验分别记录在本机 reports。该实验使用独立QA会话与单次请求只读工具白名单，默认不请求模型；每个显式场景持久保留提交号，未知结果不重发，`--collect` 只收集。只有实际工具事件能证明模型调用了资料/查询，回答中声称“我查过”不算证据。资料可读和配方查询通过，不等于装备已经制作成功。
