# 工程班次衔接与源码捕获效率

2026-09-14 10:15 的只读观察发现，天神已自然提交候选 `85ec3be`，并取得后续 124 次测试通过回执，但 08:55 起八个工程班次连续触及 360 秒截止。它并未停在旧 unknown 锁：每次原生截止正常收口，下一班继续运行。最近一个完整中断会话（10:05–10:11）在前四分半反复展开旧案、整天记忆、已经读过的差异，随后 `engineering_status(capture_source=true)` 用时 67.3 秒；直到截止也没有排出新的测试。这是观察到的具体一轮，不能推定所有八次原因完全相同。

本改动保留原角色、模型、生活/班次会话、360 秒调度及固定批准测试。它提供更快的真实证据和可继续的进度，不新建模型循环，也不替角色选择工作。

## 从真实回执接续

`engineering_status().progress` 返回最近八项测试与四项提交。它只读受管请求、测试回执和提交日志，不扫描候选源码、不返回整份测试日志、不运行模型。记录按文件时间排序仅用于限制索引，时间不是源文件验收依据；超出列表时明确返回 `testsTruncated` / `commitsTruncated`。

- `passedFixedPlan`：历史回执与原请求绑定一致，且固定计划及镜像仍匹配。它不表示当前文件已通过。
- `currentSourceMatches`：只有本次明确完整捕获源码时才比较；默认 `null` 表示未验证当前字节。
- `recentCommits[].isCurrentHead`：受管提交是否就是当前 HEAD；`pushed=false` 继续表示仅本地提交。
- 记录损坏、错配或不可读会进入 `errors`，不会把它转换成通过。

班次先看这个索引，再展开一个具体事项。已有 passed job 时可直接调用 `engineering_commit` 并传入其 sourceSha256：提交函数本身仍会完整读取当前文件、检查固定批准哈希和测试身份，变化就拒绝。因此不必先全量 `status` 再让 `commit` 重扫一次。新的测试仍先取得新鲜源哈希，`engineering_test` 仍独立重验全部字节。

班次提示和工程技能引用约定：一次推进“收回执并提交”“修改并排队测试”或“附证据交接”中的一步；记忆末段记下工单、路径、job/sourceSha256/commit、已验证结果和下一步。保留原生记忆系统，由模型自己读写；不添加另一份容易与真实回执冲突的人工进度数据库。

## 完整捕获加速

旧捕获针对每个文件都反复检查直到根路径的所有父目录，再串行读取文件。Windows Docker bind 上大量小文件元数据往返占据了大部分时间，Git 自身仅约 1.5–1.9 秒。

新捕获仍逐字节读取每一个受管/未跟踪源文件、计算每份 SHA256 和 Git blob ID，并保持同一份有序清单格式。没有跨次缓存，不用大小或 mtime 代替读取。

生产 Linux 上，单次捕获用 `O_NOFOLLOW` 和目录句柄访问文件，每个父目录只打开一次；四个短暂的 I/O 工作线程重叠 bind 往返，最多排队 16 个读取请求，结束后全部回收。它们不是常驻 Agent 或守护进程。总计 128 MiB 字节预算在读取前用同一把锁预留，不因并行放大允许捕获的总量。

每个文件须为单链接普通文件，拒绝软链接、硬链接、目录和 FIFO；读取前后的文件身份、长度和修改时间必须一致，最后再核对命名路径。所有已打开目录在接受结果前按名称与句柄重新核验，目录替换/改为链接会拒绝整个捕获，不能将旧目录内容认证为新的工作树。Windows 原生执行保留逐文件完整路径检查回退。固定 Git 模式、合并/子模块拒绝、分支绑定、批准测试哈希、覆盖范围、隔离计划和未知请求防重逻辑都保留。

## 验证

真实候选只读挂载于临时、无网络 Docker 容器，对比旧实现与新实现；没有修改候选文件、暂停 Cron、调用模型或重启服务。

| 同一候选 | 旧捕获 | 新捕获 |
| --- | --- | --- |
| 文件/字节 | 852 / 7,543,738 | 完全相同 |
| HEAD | `85ec3be50cf7a7d221d2c9221e5b717f7d9c6275` | 完全相同 |
| 源 SHA256 | `2a29060d8980a01e92661ac3ea71df98c12ac2ba058736afa7a5e7d2a8ae73ba` | 完全相同 |
| 总耗时 | 44.740 秒 | 3.888 秒 |
| Git 部分 | 1.874 秒 | 1.676 秒 |

这一对照约快 11.5 倍，完整 snapshot 字典相等，包含文件清单、SHA、模式、工作改动与基线差异。实测报告在 `runtime/observation-20260914-1013/engineering-capture-performance.json`。它是该次采样，不承诺所有负载下恒定耗时；自然工程班次是否减少超时仍须部署后观察。

初版只有目录句柄、没有有界并行时曾测得 28.3→39.1 秒，未按性能改善交付；该原始报告保存在 `engineering-capture-single-thread.json`，不覆盖历史结果。

Linux 工程回归 32 项通过，包括真实 Git 提交与字节变化拒绝、父目录/root 替换、链接/FIFO、并行总预算、进度不伪造当前验收和错配回执。班次回归 Windows/Linux 各 13 项通过。Windows 工程回归执行 32 项：29 通过、3 项仅限 Linux 目录句柄/FIFO 的测试跳过。

Windows 验证另发现 Python 3.12 的 `fstat().st_ctime_ns` 与 `Path.stat().st_ctime_ns` 在文件修改后含义不同：前者可报告变更时间，后者仍为创建时间。现分别对比读取前后同一 API 的时间，并用 inode/device 对应两个视图；不降低 Linux 校验、不将时间用于跨次哈希复用。线上部署与自然班次验收由主任务执行，本页以上性能测试不代表代码已加载到游戏 Qwen。

## 部署同步

由主任务在原生角色安全窗口加载 `/ops/engineering_workspace.py` 与 `world_team_schedule.py`。前者在天神 `qd_engineering` MCP 子进程中，须让该原生 driver 重新加载；后者是游戏 Qwen 的原生 Cron guard 调用路径，须在受管流程加载新代码。

`team_job('operations:mc-god')` 只改变任务正文及 request input。用原生 Cron GET 取得原 job、保留原 id/name/schedule/runtime/dispatch/enabled/meta，将本次正文和 request input 同步后 PUT；不要重新创建会话、改模型或误操作宿主 Qwen。现有 `configure_world_team --mode files` 不会改已存在 Cron 的正文，不能用它冒充同步完成。

工程技能引用按原生 File API/ETag 更新给实际持有 `qd-world-team` 的角色，再原样保存其 SKILL.md 并启用以刷新原生扫描缓存；不修改人格和用户笔记。主任务应按实际生产加载、原 job 读回和下一自然班次的工具回执另验，不能为使历史健康报告变绿而改旧来源哈希。
