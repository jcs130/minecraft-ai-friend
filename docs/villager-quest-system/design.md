# 村民派发任务系统：设计文档

> 状态：设计稿，2026-11-20。本文只描述代码仓库里的方案。**正式服千灯纪没有任何改动，也没有连接过。** 文中标"待验证"的机制，都还没在 Youer 上实测过。

## 0. 目标与边界

- 让村民（真正的 NPC 居民）更聪明：能闲聊、记得发生过的事，能根据村庄处境**发委托**、请英雄帮忙，从而推动剧情。
- 英雄是常驻 Agent（Numen 身体 + Python Harness），有玩家形态的身体，能打怪，负责守护村庄、接委托、去执行。
- 村民和英雄之间用**任务桥接层**连接。村民负责"编故事、提需求"，英雄负责"做事"，服务器负责"验收"。这样可以少写手工剧情节点。
- 三条硬规则：
  1. 模型说的话不能直接当成"任务完成"。完成必须有服务器观察到的证据，沿用 AgentFriend"不以语言模型评价或玩家自报判完成"的原则。
  2. 奖励数额不由模型决定，由配置表按难度给出。
  3. 发委托的村民身份来自配置，不从聊天文本里取。

## 1. 整体架构

```
┌──────────────────────── 玩家层 ────────────────────────┐
│ 玩家：和村民聊天、看委托公告、可以协助或旁观英雄            │
│ 入口：右键 Citizens NPC / 聊天呼名 / /ds chat              │
└───────────────┬───────────────────────────▲───────────┘
                │ 对话                        │ 村民播报（结果、谢礼、后续剧情）
┌───────────────▼──────────── 村民层 ───────┴───────────┐
│ Citizens NPC（身体、站位、路点）                          │
│ 米饭 DeepSeek 插件（日常对话：chatSystem 人设 + prompt 知识库 + tools）│
│ 【新增】村民编剧器 qiandeng-villager-quests（小型 Bukkit 插件）│
│   · 规则触发器：夜间怪物逼近、作物歉收、商品缺货……         │
│   · 调用 DeepSeekApi.chat(key, msg) 生成结构化委托 JSON     │
│   · 把服务器事件（击杀、交付）写成证据信号                    │
│   · 执行反馈：让村民说话、发奖励                              │
└───────────────┬───────────────────────────▲───────────┘
                │ 委托 JSON / 证据信号        │ 反馈（台词 + 奖励发放请求）
                │ （MVP：本机文件 spool；之后：127.0.0.1 HTTP）
┌───────────────▼────────── 任务桥接层（Python）──┴──────────┐
│ agent_mc_harness.quests                                    │
│ 摄入 → 策略校验 → SQLite 存储 → 选英雄 → 派发意图             │
│ → 证据跟踪（服务器信号 / 背包快照）→ 完成或失败 → 反馈出口     │
└───────────────┬───────────────────────────▲───────────┘
                │ submit_intent（只有目标，没有可执行步骤）│ intent_state / 背包快照
┌───────────────▼────────── 英雄 Agent 层 ───────┴──────────┐
│ HarnessRuntime（规划、Graphiti 记忆、反思、Harness²）       │
│ Numen 身体（桐人等），走 Numen 权限规则和反作弊规则          │
└─────────────────────────────────────────────────────────┘
```

**每层的职责：**
- **玩家层：** 只是观众和参与者，不直接创建委托。玩家的话会影响村民的情绪和台词，但不能决定任务目标和奖励。
- **村民层：** 负责"演"（说话、生活）和"提"（提出需求）。村民层的模型输出要先被桥接层的策略过滤。
- **桥接层：** 唯一有任务状态的地方。负责幂等、生命周期、限额和证据判定。
- **英雄层：** 接到的只是一条目标（goal），由英雄自己的规划器决定怎么做。桥接层不替英雄写动作步骤。

## 2. 村民 NPC 的 AI 行为设计

### 2.1 日常循环（大部分不调模型）

| 时段（游戏时间） | 行为 | 实现 | 是否调模型 |
|---|---|---|---|
| 清晨 | 下田、巡视畜栏 | Citizens 路点；原版村民用原版 AI | 否 |
| 白天 | 摆摊交易 | Shopkeepers 现有商店；AgentFriend `VillageTrades` | 否 |
| 有人搭话 | 闲聊、答疑 | 米饭 DeepSeek，小模型 | 是（便宜） |
| 傍晚 | 盘点"今天村里缺什么"，决定要不要发委托 | 编剧器的规则触发 | 只在触发时调用 |
| 夜晚 | 回屋；有怪物时求救 | 编剧器检测附近敌对生物数量 | 只在触发时调用 |

闲聊用米饭插件现成的功能：
- `chatSystem.<角色>` 配人设。
- `prompt` 指向 `prompt/` 目录下的知识库文件，存放村庄设定、艾恩葛朗特层数、村民关系。
- `tools` 让模型读 PlaceholderAPI 变量，例如当前开放的委托数。插件 1.3.0 起支持 tools，1.4.0 起支持多轮调用。

**闲聊里不生成委托。** 闲聊的回复会按 `format` 直接发到聊天栏，如果让模型在闲聊里吐 JSON，玩家会看到乱码。

### 2.2 剧情触发条件（规则先行，模型润色）

编剧器每隔几分钟检查一次世界状态。某个规则命中时，生成一个"需求"：

| 触发器 | 条件示例 | 生成的需求 |
|---|---|---|
| `night_raid` | 夜间，村庄半径 48 格内敌对生物 ≥ 6 | 讨伐（`slay`）僵尸或骷髅 |
| `shortage` | 某个公共补给箱的物品低于阈值 | 收集交付（`gather`）小麦、面包等 |
| `hero_absent` | 某个村庄超过 N 天没有英雄来过 | 一次"想念英雄"的低价值委托，可选 |
| `story_beat` | 剧情弧推进到某个节点（BetonQuest 标签或 QiandengjiRpg 层数） | 剧情委托（扩展阶段） |
| `player_milestone` | 有玩家通关某层 | 村民庆祝或请求下一步调查（扩展阶段） |

规则决定**要什么**，包括类型、目标、数量范围和难度范围。模型只负责**怎么说**，也就是标题和故事文案，再在允许的范围里选一个具体数值。

### 2.3 派发逻辑

1. 规则命中，生成需求：类型、允许的目标、数量上下限、难度上下限。
2. 编剧器调用 `DeepSeekApi.chat("委托编剧", prompt)`。prompt 里带上需求、村民人设和"村庄编年史"摘要，要求模型只输出一行 `[委托]{...}`。
3. 编剧器解析这一行，补上**配置里**的村民 ID 和 NPC ID，写入 spool。
4. 桥接层二次校验，见第 3.2 节。不合法就进 `rejected/` 并记录原因，不做二次重试。
5. 校验通过，状态为 `offered`，村民在聊天栏发布委托公告。

**限额：**
- 每个村民同时最多 1 到 2 个开放委托。
- 每个村民每天最多发 N 个委托。
- 全服开放委托总数有上限。

## 3. 任务系统

### 3.1 任务类型

| 类型 | 阶段 | 目标 | 完成证据 |
|---|---|---|---|
| `slay` 讨伐 | MVP | 在指定区域击杀 N 只某种生物 | 服务器击杀事件（原版 `EntityDeathEvent` 或 MythicMobs 死亡事件），击杀者必须是被指派的英雄，并且在区域内 |
| `gather` 收集交付 | MVP | 把 N 个某物品交给村民或补给箱 | 服务器交付事件（AgentFriend `donate` 或编剧器的交付确认）。背包快照只显示"已备齐"，不能判完成 |
| `escort` 护送 | 扩展 | 陪村民从 A 走到 B | 村民 NPC 抵达加存活 |
| `guard` 守夜 | 扩展 | 一夜内守住村庄 | 夜间村民零死亡加击杀数 |
| `investigate` 调查 | 扩展 | 到达某个坐标或遗迹 | 位置证据，复用 AgentFriend `explore`/`structure` |
| `story` 剧情 | 完整 | 多步，由剧情弧生成 | 每一步各自的证据 |

### 3.2 委托的创建和校验

委托字段（完整定义见 `packages/agent-harness-py/schemas/villager_quest.schema.json`）：
- `commissionId`：幂等键，由编剧器生成。
- `issuer`：村民 ID，必须在配置白名单里。
- `type`、`target`（命名空间 ID，例如 `minecraft:zombie`）、`quantity`、可选的 `area`（中心点和半径）。
- `difficulty`：`easy`、`normal` 或 `hard`。
- `deadlineMinutes`、`title`、`story`。

**策略校验**（`QuestPolicy`）：
- 这个村民能不能发这种类型的委托、这个目标在不在白名单。
- 数量是否超过该难度的上限，期限是否在允许范围内。
- 该村民当前开放数和当日已发数是否超额。
- 文本清洗：去掉颜色码、`/` 开头的命令形式和换行；故事文本限制在 300 字以内。
- **奖励不读模型输出**，按 `rewardTable[difficulty]` 生成。模型多写了 `reward` 字段会被直接拒绝，因为 schema 设了 `extra=forbid`。

### 3.3 生命周期

```
offered ──派给英雄──▶ accepted ──英雄开始执行或出现首个证据──▶ in_progress ──证据满额──▶ completed
   │                     │                                    │
   └──超时──▶ expired     └──意图失败或取消──▶ failed ◀──超时（expired）──┘
任何未结束状态 ──管理员撤销──▶ cancelled
```

- 状态只能按上图迁移，每次迁移都记录时间和原因。
- 证据要去重：每个信号有唯一 `signalId`，同一个 ID 只计一次。
- 意图（intent）完成**不等于**委托完成。英雄说"我做完了"或者 Harness 把意图标成 completed，都只会把委托留在 `in_progress` 等证据。
- 如果超时前没有足够证据，委托标为 `expired`，同时取消英雄那边的意图。

### 3.4 英雄如何接和做

- 桥接层维护一个英雄名单：英雄 ID、Numen 身体 ID、能接的类型、同时能接几个（MVP 是 1 个）。
- 派发时调用 `HarnessRuntime.submit_intent(goal, agent=英雄ID, priority=...)`，**只传目标，不传步骤**。目标文本用固定模板拼出来，例如"受村民【麦田的青禾】委托：在 (x,y,z) 附近 32 格内讨伐 5 只 minecraft:zombie。期限 60 分钟。"。故事文本只作为引用材料，不会进入可执行字段。
- 怎么走、怎么打，由英雄自己的规划器决定，仍然受 Numen 的权限规则、Body 安全层和反作弊规则约束。

### 3.5 完成后的反馈

桥接层在每个关键状态（offered、accepted、completed、failed、expired）都会向出口写一条反馈：
- `text`：村民要说的台词。MVP 用中文模板，扩展阶段可以接一个"润色器"，用小模型改写，失败时退回模板。
- `rewardGrant`：只有 completed 才有，包含领取者、绿宝石、Vortex 经验和声望。由服务器侧组件发放，并以 `questId` 作为幂等键，避免重复发。
- `chronicle`：写进"村庄编年史"的一句话，供下一次闲聊或委托的 prompt 引用。这就是"村民记得英雄帮过忙"的来源。

## 5. Token 成本控制

| 场景 | 模型 | 频率控制 | 说明 |
|---|---|---|---|
| 村民日常闲聊 | 便宜的 Flash 档，例如米饭文档给的 `deepseek-ai/DeepSeek-V4-Flash`（硅基流动），或本仓库已经在用的 DeepSeek V4.1 Flash | 米饭插件 `playerChatAiSize` 控制上下文条数，`duration` 控制免呼名的时间；1.4.0 自带长聊天防刷屏 | 回复限制在 100 字以内（写在 role 或 prompt 里） |
| 委托生成 | 同上的 Flash 档 | 只在规则触发时调用；每个村民每天 N 次；全服每小时上限 | 一次调用只生成一个委托 |
| 反馈台词润色 | Flash 档或干脆不用 | MVP 直接用模板，不调模型 | 调用失败就退回模板 |
| 剧情弧大纲 | 大模型，例如 `deepseek-v4-pro` | 离线批量，每周或每层一次，由管理员审阅后启用 | 只生成大纲 JSON；具体委托还是交给 Flash 档填写 |
| 英雄执行 | 现有 Harness 路由（System 0/1/2） | 已有预算 | 不归本系统管 |

**省钱的手段：**
1. **规则先行：** 只有触发器命中才调模型，闲聊之外没有定时轮询模型。
2. **固定前缀：** 人设和知识库放在 prompt 的最前面，保持不变，有利于提供商的上下文缓存（DeepSeek 官方 API 有前缀缓存计费。米饭插件发出的请求结构是否能命中缓存，待验证）。
3. **预算账本：** 编剧器按村民记录每日调用次数，超额后当天只用模板。
4. **大模型降级：** 大模型只做离线大纲，在线不用。

## 6. 风险和待验证项

| # | 项目 | 风险 | 验证方法 |
|---|---|---|---|
| 1 | 米饭 DeepSeek 1.4.0 在 Youer build920 上能否工作 | 插件声明 `api-version: 1.13`，支持 Paper、Purpur、Folia，但没有 Youer 的实测记录；它通过 softdepend 挂 Citizens，NPC 点击监听是否被 Youer 的混合事件桥正常分发，未知 | 隔离 Youer 测试服：装 Citizens 2.0.35 和 DeepSeek 1.4.0，绑定 `npcId`，右键对话，跑 `/ds chat` |
| 2 | 米饭插件**没有"AI 回复"事件** | javadoc 只公开了 `DeepSeekApi.chat(...)` 同步方法，返回 String，没有可监听的事件，所以不能拦截闲聊输出 | 编剧器主动调 `DeepSeekApi.chat`，而且必须放在异步线程，因为它会阻塞网络请求（阻塞行为待验证） |
| 3 | Bukkit 插件和 Python 桥之间的传输 | MVP 用本机文件 spool，简单但有延迟和文件锁问题；换 HTTP 要处理鉴权 | MVP：原子写（先写临时文件再改名）；扩展阶段：只绑 127.0.0.1 的 HTTP，密钥放 `.secrets` |
| 4 | 击杀归属 | Numen 身体打死怪物时，`EntityDeathEvent.getEntity().getKiller()` 能否拿到英雄（Numen 是假玩家还是实体），未知 | 测试服里让 Numen 打一只僵尸，看事件里的 killer |
| 5 | 提示词注入 | 玩家在闲聊里诱导村民"发一个 64 钻石的委托" | 委托不在闲聊里生成；奖励按表给出；字段白名单加 `extra=forbid`；村民 ID 取自配置 |
| 6 | 奖励通胀和刷单 | 英雄或玩家反复刷委托 | 每日限额、证据去重、`questId` 幂等发放，绿宝石总量进日报 |
| 7 | 英雄忙或不在线 | 委托一直没人做 | 派发前检查英雄空闲；超时转 expired，由村民说一句"没关系，下次吧" |
| 8 | 英雄执行越界 | 0.1.5 的 Numen 走路会挖方块、放方块 | 沿用 Numen 权限规则（只走不挖的身体配 deny 规则），以及起始之城的保护 |
