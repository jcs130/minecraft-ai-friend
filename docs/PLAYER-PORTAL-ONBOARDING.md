状态：2026-10-22 用户提出的新接入要求，已同步给网站维护会话；本文为实施契约，**不表示正式服已启用新准入门禁**。Agent Skill 已单独交付，见 `QIANDENGJI-AGENT-SKILL.md`。

## 用户流程

**所有真人都必须先在网站注册并绑定游戏角色；允许正版和离线账号。正版不是统一准入前提。** 网站注册和角色建立/绑定可合并为一次引导：

1. 注册并登录网站，选择“正版角色绑定”或“离线角色注册/绑定”。网站注册不以微软账号或 Java 正版为前提。
2. 正版分支通过正版启动器认证，或完整网页游戏认证证明本人的 Java UUID，绑定后免游戏密码登录。离线分支在网站设置独立游戏密码，用本人游戏名和密码登录；已有角色先核验归属，不能覆盖旧账号或进度。
3. 首次绑定可在安全认证大厅完成，再放行游戏世界。未在网站登记/绑定的真人不能进入世界；认证大厅的证明操作不等于正式准入。
4. 官网提供当前匹配的真人客户端整合包、版本、加载器、安装方式、服务器地址和 SHA256。

正版分支也可增加“使用微软账号登录”。应采用 Microsoft 官方 OAuth 授权码、PKCE 和 OIDC 流程，仍须核验该用户的 Minecraft Java 游戏身份。微软邮箱或网站 ID Token 本身不能当成已验证的 Minecraft UUID；网站不接收微软密码，不把访问/刷新凭据放进客户端整合包。这是可选的正版绑定方式，不能阻止离线玩家注册。

官方参考：[Microsoft identity authorization code flow](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow)、[Minecraft 所需账号](https://help.minecraft.net/hc/en-us/articles/19615552270221-Accounts-Required-to-Play-Minecraft)。游戏角色证明优先复用当前代理真实认证结果，具体可用路径以认证桥部署状态为准。

## 身份与准入

- Java 正版真人：正版挑战通过的 UUID + 网站有效绑定；通过后免游戏密码。
- Java 离线真人：网站注册、游戏角色有效绑定及独立游戏密码；登录时核验该角色密码。
- 基岩真人：已验证的 Xbox/XUID 身份 + 网站绑定，不要求购买 Java 版来证明基岩身份。
- 外部 Agent：网站登记的角色与独立接入凭据，用户的 Agent 自管 loop/记忆。不能仅因昵称以 ag_ 开头就获得真人准入的豁免。
- 管理员、观察者、现有角色先逐项保留真实 UUID、归属和进度，不通过重建玩家或覆盖原密码迁移。

当前 LoginGuard 0.1.4 候选代码具备 `/portal bind` 和短期一次性请求，通用 `portalProof` 同时允许正版验证和已设置密码的离线账号，符合两种归属验证方向。正版绑定分支单独校验 `premiumVerified`；离线分支核验本人原密码，未设密码的首次临时放行不能当成归属证明。最终统一门槛是网站有效登记/绑定，不要求所有真人都通过正版校验。

候选 `portalCreate` 当前只允许 ag_ 前缀的 Agent，新建离线真人角色还需单独开放普通玩家注册操作，保留角色唯一性、原账号归属与保留身份约束，不能只改网页文案。现有绑定证明要求 `inPaper`，若改成“先绑定才能进世界”，需要把首次绑定安排在认证大厅或通过完整网页游戏认证，避免互相等待。

## 游戏内和网站改密保持一致

用户要求保留游戏内改密，并与网站的游戏角色密码管理一致。**LibreLogin 账号库是游戏密码的唯一权威来源**：游戏内 `/changepassword`、首次设密，以及网站的角色注册/改密最终都更新同一 UUID 的同一份凭据。网站不保存另一套可用于认证或回写的游戏密码/hash，不通过同步两份数据库来维持一致性。

网站自己的登录密码用于所有者账号，一个所有者可以管理多个游戏角色；它与各角色的游戏密码分别管理，页面明确标注。修改某角色的游戏密码不会顺带改网站所有者密码，也不会影响其他角色。

- 网站核验当前游戏密码时，读取认证端最新凭据，不能使用页面加载时的旧值、云端快照或缓存。游戏内改密提交成功后，旧密码立即不能用于后续网站角色改密，新密码可以。
- 网站改密只在认证端持久化并返回原 requestId 的成功终态后显示成功。随后游戏的新登录使用新密码；失败或未知结果查询原请求，不自动重发、回滚为旧密码或补写旧快照。
- 同一 UUID 的两端并发改密须由认证端一致处理；提交时再次核验当前凭据或版本，过期请求明确失败。仅持有某个加载出来的用户对象锁，不能在未验证数据库/原生改密路径的情况下宣称跨入口原子性已成立。
- 网站/云端只保存和展示 passwordSet、变化时间或已实现的凭据版本等非秘密元数据，并保留来源和采样时间。游戏密码、hash、微软凭据不进入角色只读 API/PAT、普通状态快照、审计正文或日志。认证桥不可用时禁用改密，不能先显示成功再等待同步。
- 玩家/Agent 客户端记住的旧密码会失效，由持有者更新本人私有凭据；服务器不把新密码广播给其他连接，也不把它交给模型。

2026-10-22 只读审阅候选代码：网站 `GameAccounts` 将加密改密请求交给 `PortalBridge.Accounts.password`，`LoginGuard.portalPassword` 使用 LibreLogin provider 更新账号；网站 Store 保存其所有者密码和角色操作元数据，没有独立的游戏密码字段。**这仅确认当前调用方向，不代表双向改密及并发一致性已实测通过。** 已将以下验收要求同步给负责网站/认证桥的会话：

1. 独立 QA 角色用游戏命令从 P1 改到 P2，网站游戏密码管理拒绝旧 P1，使用 P2 可继续改为 P3。
2. 网站确认 P3 已保存后，游戏旧 P2 登录失败、新 P3 登录成功，原 UUID、角色归属与物品不变。
3. 并发/延迟改密请求按当前凭据或版本判断，不能覆盖后来已经生效的密码；重复 requestId 不重复执行，未知结果可查询。
4. 网站缓存、云端快照或服务重启不会把旧凭据恢复；网站所有者密码、其他角色及现役玩家保持原状。
