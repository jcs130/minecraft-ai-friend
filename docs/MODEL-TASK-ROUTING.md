# 大模型统一交给 QwenPaw Agent

2026-09-13 路由修复：当前 10 个启用角色统一在游戏 QwenPaw 18089，宿主 8088 保持原用途，旧运营实例留在归档 profile。以下旧实例、额度和人物部署描述属于早期记录，以根 AGENTS 的最新运行状态为准。

运营用途保留原名称和历史：`operations.diagnostics` → `qd-engineer`，`operations.events` → `qd-guild-planner`，`operations.controls` / `operations.exploration` → `qd-survivor`。这是职责目录，不是通用后台派工入口。当前 world 消费者只接受五项 `world.*`，NPC 只接受原三类用途，生活控制器只使用 `survivor.autonomy`。活动通过团队工单/原公会入口，体验通过团队工单交原生活会话处理；不会为桐人创建第二条生活推理循环。

`operations_delegate` 只允许逻辑角色 `mc-god`（实际 `game:qd-engineer`）完成一次运营证据报告；原生请求根角色跟随司灯当前宿主 `qd-steward`。四个停用/休眠角色不接受新委托，但原账本、角色署名、原任务 ID 与记录的宿主保留，旧回执仍可查询。工单创建、原生任务受理、实际执行和完成验收须分别核对。

迁移后运营 MCP 不依赖父容器的状态目录环境变量：Qwen 的子进程环境白名单会过滤它。`operations_state.py` 依据已验证的逻辑角色和原生 `--native-runtime/--native-role`，将游戏托管运营角色的报告、规划请求和派工账本绑定到 `/operations-state`；原运营实例仍使用 `/state`。`WorldPlanning` 必须显式复用 `OperationsTools.state`，否则工具回执可能成功但文件仍落在游戏目录，NPC 消费者读不到。首次实机暴露的原报告/请求保持原字节、ID 和时间交接到共享目录，不重新调用司灯。

2026-09-08 后续设计：用户要求每位女仆拥有独立人格 Agent，复用原生能力为 MCP。已核实的接口、身份桥和实施边界见 [女仆独立 Agent 设计](MAID-AGENTS-DESIGN.md)。当前本文描述的共享文本入口仍在线，独立人物与身体工具尚未部署。

所有生成式模型推理由 QwenPaw 里的具名 Agent 执行。游戏代码只提交任务、读取结果并校验游戏行为，不配置供应商密钥、不自行选择云模型，不在失败后另换角色再请求一次。

入口目录为 [model-task-routes.json](../config/model-task-routes.json)。目录声明用途、QwenPaw 实例及 Agent ID；具体模型和供应商留在原生 QwenPaw 控制台。新增职责先注册角色、设置有限工具/预算、加入用途目录并验证，再启用调用者。不是每条聊天或每位村民创建一个常驻 Agent，也不允许环境消息随意派生角色来扩大预算。

## 费用和失败处理

world 的五类推理和桐人的规划读取同一目录；运营继续使用原生角色委托。world 删除了传令失败后改派天神、后台任务异常后再发同步请求的路径；任务 `timeout` 修正为 570 秒，HTTP/轮询仍用毫秒。未知提交不代表模型没有执行，不再自动重复付费。

村民、公会和女仆共享一份持久任务账本，三类用途分别限额：村民对话 4 次/滚动24小时、间隔300秒；公会整批策划1次/滚动24小时；女仆24次/滚动24小时、间隔60秒。对应用途下所有人物共享额度，新角色或新会话不增加额度。提交先预留，随后记录原生 `taskId`；读取状态至少间隔10秒，不调用模型。原有桐人48次决策/滚动24小时、180秒冷却，以及运营4次派工/滚动24小时保持不变。

这些是自动业务提交限额，不是账号金额或控制台人工对话总额。人工在 QwenPaw 发起对话仍受其模型并发、QPM 和迭代限制，但不经过业务提交账本。一次决策/派工也可能产生多次模型请求，应在 QwenPaw 用量里看真实调用。

普通村民环境闲聊仍用原模板（`NPC_LLM_ENABLED=0`）；独立开启 `NPC_GUILD_AGENT_ENABLED=1` 不会同时唤醒整村闲聊模型。语音识别、语音合成和本地向量检索属于专用非生成服务，保留原运行方式；没有把录音、配音、RCON 或方块扫描变成付费 Agent 对话。

## 任务策划如何进入公会

策划一次读取整批已绑定、职业适合的发单人及物资白名单，生成指定日期的结构化候选。游戏服务重新检查日期、UUID/职业绑定、材料 ID、数量3–24、奖励1–3绿宝石、每人最多一张和文本长度。模型不能在方案中执行命令、直接发奖或宣告玩家完成。

预案写入独立的 `server/mcdata/village/agent-plans/YYYY-MM-DD.json`。当天正式任务已经存在时不改写；新日读取通过验证的预案，再异步准备下一日。无可用预案时沿用已有合法模板。领取、实际物品交付、狩猎/到访验收和功勋继续由原公会执行。

NPC进程中的受监督收集线程每45秒只读查询已有待完成预案，及时把结果保存到磁盘，避免等到次日才读取已经过期的原生任务。无预案或预案已完成时不访问QwenPaw；收集线程不能提交模型任务，旧的并发响应也不能覆盖已完成结果。

```powershell
# 在现有 NPC 容器中按需提前规划明日；会占一次策划额度
docker exec qiandengji-npc-1 python /opt/sidecar/npc_planner.py --submit
# 只查询同一个任务，不再次调用模型
docker exec qiandengji-npc-1 python /opt/sidecar/npc_planner.py --poll
```

## 女仆兼容入口

女仆模组使用 OpenAI 格式的文本接口，薄适配器运行在现有 NPC 服务的受监督线程里，内部地址为 `http://npc:8091/v1/chat/completions`，不发布宿主端口。它只校验内部令牌、转换消息、调用固定 `qd-maid-dialogue` 并返回原协议文字；自身不持有供应商凭据或运行模型。

迁移保留全部站点 ID，把站点都指向该入口；原未启用站点保持关闭。历史模型标签兼容接受，但实际模型由 QwenPaw 角色选择。原完整配置保存在忽略的私有备份，TTS/STT 和女仆身份不改。`tlm ai_chat reload` 可让运行中的模组重载，无须重启 Minecraft。

相同消息历史使用稳定请求摘要，跨午夜或 HTTP 超时后仍复用原生任务，不重新付费。当前桥只支持文本对话/设定，不返回模组函数调用，不支持图片/流式接口；不能宣称女仆模组的全部 Agent 工具已迁移。缺少逐任务 Token 时响应不伪造用量，真实统计在 QwenPaw。原 `smoke_maid_model.py` 和 `local_model_config.py` 的直接 LLM 请求/旧密钥恢复路径已退役。

## 注册和验证

`tools/register_world_agents.py --check` 只生成检查结果。应用三位角色时先让桐人暂停且无未决动作，停止游戏 QwenPaw 与 survivor，再运行 `--apply qiandengji`。脚本备份并最后更新角色索引，重复运行保留模型选择和会话。用镜像内的 QwenPaw 2.2 Schema 和 AgentBuilder 做离线验证，再启动服务。`tools/configure_maid_agent.py` 分别支持 `--check` 与 `--apply qiandengji`，保留私有站点备份。

健康检查核对路由目标、角色限制、女仆站点与令牌匹配、NPC 线程，以及单独记录的原生任务冒烟；不会为了健康状态周期调用模型。运行证据位于忽略的 `reports/model-routing-smoke.json`。生成候选不等于发布生效，接口文本回复也不等于实体女仆完整游玩验收。
