# 结衣忙时累积对话

结衣的正常 TLM 对话改为先持久收件，再由原生活会话消费。收件不启动模型，不打断当前回合；原 QwenPaw 每十分钟生活信号、原角色和 session、单并发及现有 NPC 工作线程继续使用。没有增加驻留进程。

## 为什么原来会拒绝

旧链路有三处占位：Java 每个身体一次在途 HTTP、Python 全局一次同步等待、Qwen 当前人物的模型任务。收到新消息时只会返回忙碌，不能把新输入保存为待处理感知。队伍 `party_send` 本来就有自己的持久消息与游戏 heard 回执，这次没有替换它。

新的 Java 请求通道只等待收件，最多八个并发 HTTP；Python 短收件通道与旧的长模型等待分开。只有精确绑定结衣/桐人、在线 Numen 主人及正常 `LLMCallback.class` 才使用新协议。其他人物、角色设定生成与历史摘要保留同步逻辑。

## 收件与消费

1. 原生游戏提供身份和最新用户消息；Java 不再重复传输整段旧聊天历史。HMAC 验证后，Python 校验现有角色注册表与生活消费者的身体、主人、角色及原 session 一致，不自动创建人物或修改配置。
2. 输入写入 `server/mcdata/village/party/dialogue-inbox/perception-inbox.sqlite3`，事务持久化后才返回 HTTP 202。响应是七字段收件凭据，不含 `choices`。Java 仅清除原等待气泡，不添加助手历史、台词或 TTS，也不显示模型失败。
3. 下次正常生活信号把最多八条完整输入冻结在该轮的 `privateDialogueInputs`。序列化批次最多一万字符，并受 Qwen 单次总提示二万四千字符限制；剩余完整消息继续留在磁盘。`observedAt` 保留游戏发生时间，`receivedAt` 保留网络收到时间，不能把网络到达顺序误作原发生顺序。
4. 控制器先保存原任务 key、提示及精确 `inputIds`，然后认领这批消息。只有同一任务完成才把对应 ID 标记 consumed；该轮中途到达的输入不会被一起确认。
5. native 结果未知时保留原 claim/key，只查原任务，不新建任务重发。失败的批次保留 failed 证据，不自动重放可能已经执行的工具。控制器写入中断后，原批次可以幂等恢复。

相同 request ID 与相同签名字节只确认一次；同一句话的新 request ID 仍是一件新的真实输入。最多保留4096件事件，满时明确拒绝，不悄悄删除未读资料。单条最多8000字符，另按实际 JSON 转义后长度验证，避免接收一条永远装不进上下文的消息。上下文暂时放不下队头时报告 `headDeferredByContextBudget`，保留原文，不为清队列另开模型循环。

consumed 表示已进入并完成该模型回合，不表示每一件建议都执行了，也不表示已经对玩家答复。

## 私有内容与游戏交流

实际 TLM 1.5.3 的 `LLMCallback` 只有身体与主人，没有可靠的实际发言者 UUID。主人不能自动视为发言者。因而新收件固定为 `source=tlm_native_dialogue`、`speakerVerified=false`、私有环境数据，不能改变权限，不能把私有原文或回答转发到队伍/公开聊天。

结衣自行决定哪些内容应结合目标理解、记录、暂缓；不会被要求每条输入都回一句。桐人与结衣已经真实 heard 的队伍交流仍沿原游戏机制处理。这里没有实现普通真人 TLM 对话框的延迟逐条回答，也没有把202收件凭据伪装成角色答复。
