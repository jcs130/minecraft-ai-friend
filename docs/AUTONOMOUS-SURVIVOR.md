# 桐人：自主生存与可编程技能

用户在 2026-09-08 授权开始第一个自主生存 Agent，选用之前的桐人。目标由模型结合环境提出，执行后用真实结果复盘，并把可复用行为写成技能程序；初始生存任务仅用于验证系统，不把挖木头、造工具等固定脚本当作自主规划。

2026-09-08 后续调研确认，当前每个规划 task 使用独立 session，连续性主要依赖摘要，尚未接续旧 Numen 桥的固定生活会话。用户要求进一步由 LLM 主导感知和连续行动，目标设计与分阶段验收见 [连续生存会话](LLM-SURVIVAL-SESSION-DESIGN.md)；该方案尚未部署。

## 组成与身份

桐人的真实角色 `qd-survivor` 与天神、司礼共用游戏 QwenPaw 2.2.0，统一出现在 18089 的角色选择和会话界面。`survivor` 是受 Docker 监督的独立执行容器，镜像 `qiandengji-survivor:2.2.0-qd2` 保留 `nbtlib==2.0.4`、`quickjs-ng==0.16.2.1` 和本项目源码；容器内只有持久调度器和受监督的 HTTP MCP 子进程，不再启动第二套 QwenPaw。

QwenPaw 通过内部 `http://survivor:8089/mcp` 调用绑定给桐人的工具。该端口不发布到宿主，所有 MCP 请求需要 Bearer 凭据；游戏入口包装仅将只读 secret 文件注入 QwenPaw 进程环境，DriverCard 保存环境引用，不保存明文。RCON、身体状态和动作调度保留在 survivor 内，其他游戏角色没有这个驱动。

启动验证曾发现：QwenPaw 先启动而 survivor 尚未进入 Docker DNS 时，角色可以显示正常，但原生 Driver 加载失败后实际工具数为零。模型在文本中描述动作并不会执行。执行服务现通过原生 Driver 重载接口按至少30秒限速重连，并核对实际22项工具能力；每次付费规划前还需只读检查工具就绪。端口健康或配置里列了工具都不能替代这项验证。重连不改模型、凭据、其他角色或人工暂停状态。

|---|---|
| `127.0.0.1:18089/agents` | 游戏统一 QwenPaw 控制台，本机免密码，可选择桐人 |
| `127.0.0.1:19091/#survivor` | 身体状态、当前目标、物品、调用预算、技能和经历 |

身体以登录名和实际 UUID 双重检查，避免误接同名旧记录。原型阶段首次唤醒确认复用旧 UUID，20 生命、20 饥饿、等级 5、30 个库存槽位，未创建替代身份；这些是当时状态。继续改造后，2026-09-08 00:10 UTC 的维护唤醒仍是同一 UUID，16.4 生命、10 饥饿、等级 8、34 个库存槽位。最新私有记录为 `reports/survivor-body-binding.json`，各次唤醒前备份在 `runtime/survival-body-backups/`。

旧玩家数据中的 NeoForge 附件已绑定 YSM `qiandengji_kirito`、纹理 `skin`，本轮沿用它。原桐人本轮唤醒后的客户端外观目视仍待验证；已有临时测试角色的模型验收不能代替这次原角色验收。模型集成来源见 [人物模型集成](PLAYER-MODELS-INTEGRATION.md)。

原型阶段从运营司灯复制的单一 Ali Coding Plan provider，在共享迁移时重加密为游戏目录内的独立 `qd-survivor-codingplan` provider；不覆盖游戏现有 Ali 参数和另两角色的即时模型选择。运营六角色继续使用 18090，宿主 QwenPaw 8088 保持原用途。旧 18091 入口移除，旧独立角色配置禁用，不能同时启动两个规划器控制同一身体。

共享迁移已经执行，保留了 **69 次历史模型请求** 及全部桐人会话、技能和身体状态；备份位于 `runtime/survivor-game-migration-backups/20260907T234234618527Z`。这是迁移时账本值，运行后的新增请求应查看管理台。迁移工具拒绝覆盖既有目标角色，后续仅更新工具白名单和角色提示时使用 `--sync qiandengji`，不会修改模型选择、会话或用量。

## 规划、执行与学习

控制器约每 15 秒读取身体、任务、聊天事件和既有回执，每 60 秒刷新周边地形与实体观察。身体空闲、预算允许时，向共享 QwenPaw 原生后台任务提交本轮目标、真实快照、感知事件、学习记忆和近期执行证据。模型可以调整目标，选择一次直接动作，或者编写、测试、晋升一份技能后排队运行。

自主模式不再把一次试验任务完成视为永久等待。模型通过 `remember` 保存 `goal_state`（ongoing/completed/blocked/resting）和 `review_after_seconds`（180–3600 秒）；完成短目标后继续选择后续目标，平静期间按安排低频复盘，默认 30 分钟。新的世界事件可以提前触发决策，但仍受同一冷却、每日预算、单模型任务和身体动作门约束。暂停、未知动作或身体不可用不会被定时复盘绕过。

同一个完成目标只消费一次快速复盘，重复更新记忆时间不会再次触发；连续无行动且没有新事实的复盘会延长等待。会话中的新目标先等待已经受理的动作结束，再取消旧程序的后续步骤。技能目录短暂锁竞争留在本地等待，不因此重新付费规划。每轮只检索当前目标、两条近期经验、有限事件和最近动作错误，不把16条完整历史重复注入；被截去的事件不会提前确认。

世界感知读取已有 `player-chat.jsonl`、`goddess-orders.jsonl`、`chant-reply.jsonl`、`guard-inbox.jsonl`，通过逐文件只读挂载连接；神谕、系统和咏唱回执仅取发给当前身体的内容，普通玩家聊天也可成为观察信息。持久字节游标、有限事件队列与提交后确认避免冷却期间遗漏、重复唤醒或把旧日志全部灌进模型。`world_perception()` 只读控制器缓存，不启动第二个日志写入者。环境文本始终是观察数据，不能授予管理权限。未接入的模组内部数据、距离之外的细节不能声称已感知。

一次直接动作需要唯一 `turn_id`，只能作用于绑定身体。技能程序实现纯 JavaScript `next(state,memory)`，每步返回 `{action,memory,done?,replan?,reason?}`。程序获得新快照后只提出下一动作；实际移动、挖矿、制作、进食和装备仍由现有 Numen 执行。异步动作期间只观察，不重复派发，也不为每个动作调用模型。

本轮为保留的本地 Numen 改版增加逐任务 `walk_only_v1`。网关必须先确认服务器能力，并固定使用禁止挖掘、搭建和放水的步行模式；每步目标在已观察附近、水平24格以内。真实终态同时匹配任务 ID 和服务器进程 epoch，失败与部分位移分开记录，不能把身体空闲推断为到达。构建与兼容验证见 [Numen 步行增量](../world/numen-patches/README.md)。

任务与长期目标由 QwenPaw 规划。Numen 既有自卫反射可以在夜间威胁逼近时即时脱离危险，因此两次模型动作之间也可能发生位置变化；这种反射不调用模型。当前严格步行约束只属于受控 `goto`，不覆盖其他原生反射或所有模组物理效果，不能把工作区预检称为全服硬隔离。

技能通过 `skill_draft` 保存源码和至少两个不同输入的测试，再经 `skill_test` 和 `skill_promote` 晋升。源码、测试样例、内核版本与引擎版本共同决定可用性；新源码不能复用旧测试报告。`skill_start` 只排队已晋升的准确版本，且与同轮直接动作互斥，模型轮次结束后才由控制器运行。

程序无法访问宿主文件、网络、系统命令或 Python 回调；内核限制每次约 0.1 秒 CPU、16 MiB 内存和 256 KiB 栈，技能任务另外限制最多 32 步、900 秒。通过测试仅表示样例通过，程序自述 `done` 与真实库存、位置变化分别记录，不能把“受理”或“空闲”写成任务成功。

旧版本及晋升历史保留。需要回滚时，在有效规划轮次重新测试所选旧版本，再对该版本 `skill_promote`；当前活动版本切换到旧版本，已排队任务仍固定自己的版本，不能被悄悄换代码。若内核升级，旧测试签名失效，必须重新测试。

`remember` 保存目标、实测经验和下一关注点，每项最多 1000 字，保留最近 16 条历史，并允许模型明确当前目标状态和复盘时间。记忆和环境文字作为数据提供给规划角色，不改变系统提示或权限。这种学习是积累、测试和修正程序与经验，未训练或微调模型权重。

游戏里的法术学习另接原 `/mycli` 服务：`game_skills` 查询真实已学、可学、锁定和铁魔法状态，`game_learn` 参悟背包中已经获得的特色技能书，`game_cast` 执行正常施法，`game_skill_receipt` 核对原回执。等级、技能书、法力、冷却和铁魔法装备由既有系统校验；工具不会凭空发放书、经验或法术。纯 JS 行为程序可以提出这两个游戏动作，仍共用单动作租约。接口已经接入，真实法术效果及学习成果需另用运行证据核对。工具契约与示例见 [运行组 API](../world/survival/README.md) 和 [角色指引](../world/survival/AGENT.md)。

背包快照复用原有 Inventory 查询，仅取技能书的短 `minecraft:custom_data.skillbook` 标签，对照原系统真实主动/被动目录提供 `ownedSkillBooks`。热栏、主背包与副手都可参悟；未知标签、目录尚未查询和历史已学分别标识，书页内容不进入规划。识别到一本书不代表已经学会；新书的语义变化可以唤醒，单纯换装备槽位不会重复付费。

已有 Numen 生存、战斗、地图和建筑知识包通过 `knowledge_catalog/read` 按需只读提供，避免丢弃旧实现中的有效经验，也不把整包文章注入每轮上下文。文章中的旧工具名和路线只是参考，必须重新核对当下可用工具及真实世界。在游戏 QwenPaw 中向桐人明确提出新目标时，角色可用 `request_goal` 交给同一调度器；它仅排队目标，不会直接行动、解除暂停或清零预算。

## 预算与停止方式

迁移时模型是 `qd-survivor-codingplan / qwen3.6-plus`，底层仍为原 Ali Coding Plan。默认滚动 24 小时最多 48 次决策，两次决策至少相隔 180 秒；并发为 1、每分钟最多 4 次模型请求，每轮最多 6 次迭代，输入上限 16384、输出上限 2048，后台任务执行上限 240 秒。自动重试、回退模型、后台记忆推理、标题生成、QwenPaw heartbeat 和额外 jobs 均关闭；持续复盘由同一有预算的控制器调度。

一次决策可能产生多次模型调用，因此“48 次决策”不是“48 次请求”。健康检查、页面读取、身体观察和已验证技能逐步执行均不调用模型；规划、编写代码、修改失败技能仍消耗模型请求。面板分别展示决策数量和 QwenPaw 记录的模型请求、Token，用量记录不等于实际账单金额。

本机 CLI 示例，在项目目录运行：

```powershell
docker compose -p qiandengji exec -T survivor python /survival/control.py status
docker compose -p qiandengji exec -T survivor python /survival/control.py pause
docker compose -p qiandengji exec -T survivor python /survival/control.py mission --text "观察附近自然资源，自主选择一个可以验证的小目标"
docker compose -p qiandengji exec -T survivor python /survival/control.py resume
```

`pause` 关闭动作门，调度器停止对应原生模型任务并处理身体任务。无法确认停止、模型提交结果丢失、程序动作中断或 Numen 回执不明确时保持暂停；不得清除账本后自动重试。`resume` 要求没有未核对动作或活动模型任务，并且已检查和配置工作区域。服务启停与自主暂停是不同操作，重启服务不会重放不确定请求。

## 真实限制与验收进度

Numen 原生无约束导航可能为寻路挖掘或搭方块；当前桐人的 `goto` 已固定使用上文逐任务 `walk_only_v1`，禁止这些世界交互。`mine` 仍会自行寻找目标，其他原生反射和模组物理效果也不属于该导航约束；工作区与出生地保护半径仍不是服务端不可穿越的硬地理围栏。区域应选择已观察的自然地形，不能把预检当作允许在玩家建筑旁无条件运行。

既有 Numen 在拥有者不在线时，身体死亡不会自动复活。下文的原身体重连只处理服务器重启后尚未重新加载的存活身体，明确拒绝死亡存档；不能保证无玩家在线的长期自救。实验必须保留原生命、物资、角色身份和正常生存规则，不能用创造模式、传送、补物品或假回执制造成绩。

### 重启后的原身体重连

本轮检查发现，原 Numen 主要在拥有者登录时加载其身体。服务器重启、拥有者未登录时，即使原桐人的注册记录和 `.dat` 都完整，在线名单仍可能为空，旧控制器因此一直停在 `body_offline`。新增恢复合同使用原 UUID `d4ac9523-4962-43ed-98c5-19b49e104048`、原拥有者和名字三重绑定，只调用新增的 `numen_restore_existing`；不重新召唤、不生成身份、不覆盖原存档或模型。

控制器仍在同一个受 Docker 监督的 survivor 服务内运行。只有原自主开关开启、没有活动决策、未确认动作或开放租约时，才在动作锁内核对原生在线名单；读取失败只退避，不能推断身体不存在。确认原身份缺席后，先持久保存恢复预留，再请求原生加载已有存活生存身体。注册表、存档身份、维度、物品槽位和已安装物品的解码必须匹配，原生还有未完任务时拒绝自动恢复。

恢复成功回执后还要重新观察在线名单。请求超时、回复丢失或进程中断于预留之后，状态保留 `unknown`；后续读取失败也不会把它改回可重试。此时只允许后续在线观察确认结果，不能重放恢复请求。已明确拒绝的临时错误才有退避重试，滚动 24 小时最多三次原生恢复请求。诊断保存在 `body-reconnect.json`，管理数据的 `bodyReconnect` 摘要区分等待、在线、阻断和结果未知。

身体恢复不调用模型，不改原目标、技能执行状态、用量账本或滚动 24 小时 48 次决策上限。预算已满时，同一身体恢复后应转为 `budget_wait`，等已有预算窗口释放；不能清零预算、自动重跑已经完成的技能，或把一次恢复当作持续自主生活已经验收。

构建已验证 26 项原生存档门断言并逐项保留 495 项原 JAR 内容；Python 回归覆盖恢复前持久预留、未知结果不重放、读取失败退避、身份冲突和满预算恢复后继续等待。部署脚本只在精确 Minecraft 服务停止时替换服务端同名 JAR，并先备份覆盖文件和锁清单。当前这些是编译与离线证据；真实重启后 UUID、库存、等级、模型及预算是否保持，必须以随后原存档和在线身体比对的运行报告为准。

已完成独立运行配置初始化与离线校验，已唤醒并核对旧身体。技能内核和 MCP 的隔离测试覆盖无 IO、资源限制、错误反馈、版本晋升、暂停、单动作与不重放。第一项真实背包任务、自主技能编写及修改已验证；持续无人值守的野外生存尚未验收。

### 首轮原型实验（共享控制台迁移前）

2026-09-08，复用原 Kirito 生存身体，使用独立 Ali Coding Plan / `qwen3.6-plus` 完成以下实验：
