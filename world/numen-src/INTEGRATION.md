## 为什么是源码集成而不是"换上游 jar"

本项目的使用场景与上游默认场景不同：**纯服务端自主 agent、无客户端接入**，且要求
严格到达、按原身份恢复身体、无客户端时身体与世界照常 tick。这些能力上游发布件里没有
（逐标识符比对过：`walk_only_strict_arrival_v2` / `existing_body_restore_v1` /
`AutonomousBodyTick` 全缺）。若继续"上游 jar + 二进制补丁"的叠法，每次上游更新都要重解一遍
class family 与哈希；**源码集成后，我们的改动有明确的落点与版本对照**，上游更新变成
一次普通的 rebase/合并。

## 我们的改动（正在迁入这棵树）

| 能力 | 目的 | 当前状态 |
| --- | --- | --- |
| `walk_only_strict_arrival_v2` | 任务内步行 + 严格到达（没真站上目标格不算到达）。**网关硬依赖** | ⏳ 待迁入 |
| `existing_body_restore_v1` | 按**原身份**恢复已存档身体（绝不 summon 新 UUID）。**重连路径硬依赖** | ⏳ 待迁入 |
| `autonomous_body_tick_v1` | 无客户端时让同伴身体照常 tick | ⏳ 待迁入 |
| `autonomous_world_tick_v2 / v3` | 只有服务端身体在场时让周边世界照常 tick | ⏳ 待迁入 |

**迁移期的权威源（重要，别搞混）**：
- **在四个能力全部迁入并通过实机验收之前**，构建输入的权威仍是
  `world/numen-patches/`（补丁 + 输入哈希 + 构建器 + 测试），本目录仅供阅读与迁移。
- 迁完之后：**本目录成为权威**，`world/numen-patches/` 降级为历史记录与能力契约说明。
- 迁移与部署需要**停服窗口**，并按 `tools/deploy_numen_*.py` 的备份 + 哈希校验路径走。
