# 查配方、补材料、验收成品

适用：千灯纪 Minecraft 1.21.1。模组和数据包可以改变配方，先查询当前服务器，不靠记忆写死模组合成表。

## 查询与判断

当本轮开放 `lookup_recipe` 时，按它的参数 schema 查询目标物品。来源是正在运行的 RecipeManager；本次覆盖标准合成、烹饪、切石和锻造，每次最多四条。返回内容可能截断，未查到不能推断物品不存在。特殊机器、自定义加工、祭坛和其他模组机制可能未覆盖；此时保留机制缺口，不假设工作台能处理。

先看配方类型、产出数量、材料及替代项。材料显示名可能没有命名空间，不直接把显示名当成物品 ID；用实际背包 `counts` 的完整 `namespace:item` 与当前可验证材料对应。模糊对应无法确定时先查清，不默认补 `minecraft:`。原生“候选组”只保留共同词缀，没有完整成员；例如 ingot 组不能推断铁锭、金锭、铜锭全都合法。没有完整候选成员证据，就把材料匹配保留为未确认，不能只因背包有同类物品就宣布材料齐全。已确认成员的替代项才可按库存选一种，不把全部替代项都当作必需材料。

查询成功只证明服务器有配方，不证明当前身体能使用对应工位。没有 `lookup_recipe` 或身体工具的角色，可整理目标、所缺信息与前置条件，不替桐人合成。

## 一个按事实推进的例子

目标是制作一把目前缺少的工具，例如 `minecraft:stone_pickaxe`。

1. 查看本轮库存、已有工具及目标用途；如果已经有更合适的工具，不为走科技树重复制造。
2. 用 `lookup_recipe` 查询该目标，读取返回的材料、数量与工位类型，不在计划里预填固定配方。
3. 对照完整库存列出缺料。缺少材料时，仅采集已观察到、允许采集的自然资源；缺少工位则先解决工位条件。保留维持生活所需物资。
4. 条件满足且本轮实际开放动作工具后，桐人才可使用本轮 `turn_id` 调用 `craft`，`item_id` 使用确认过的完整 ID；当前 `count` 是目标物品数，允许 1–16，不是固定一次只能产一件，单配方产出仍以实际结果为准。一次直接身体动作与启动程序二选一。不得拿 `craft` 试探配方或材料，因为它可能先操作合成格。
5. 等本次原生任务终态，核对前后材料消耗和成品库存。若还要使用它，再由后续动作 `equip` 并核对装备槽。受理、工作台打开或方块消失都不证明成品到手。

## 烧炼与失败

炉类加工按真实工位完成：正常打开本人或授权的容器，`inspect_container` 读取实际槽位，再用 `transfer_items` 放入匹配的原料和燃料。一次最多四项槽位搬运；观察实际进度与输出，取出后核对背包。不要把炉子“已装料”写成“已得到金属”。切石、锻造或模组工位虽然可查到配方，执行仍取决于已开放能力。

已知缺料或明确拒绝可用于改变计划；超时和未知回执不自动重发合成或搬运，以免重复消耗。单次 `status` 观察不能清除未知动作锁或授权重试；等原回执或既有管理恢复流程明确结果。把失败的具体前置缺口记录下来，避免下一轮重复猜配方。

依据仓库：`world/survival/mcp_server.py`、`world/survival/numen_gateway.py`、`world/survival/world_actions.py`。配方最终以本轮 `lookup_recipe` 的 schema 和实时结果为准。
