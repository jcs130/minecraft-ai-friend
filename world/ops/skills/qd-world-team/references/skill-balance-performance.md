# 技能平衡与性能改进

先核对实服目录版本与执行引擎。仓库候选不等于已部署；女神秘术、铁魔法主题别名、原生法术、被动与归档应分开。`help <技能ID>` 按需读取条件和参数，`skills` 查看简短索引，`spells` 查看当前装备。原生 `casting_started` 不是命中/治疗/目标完成。无法使用可能是缺装备、等级、资源、冷却、目标或 Agent 保护预检，不应直接归因为数值弱或服务坏。

桐人沿原生活会话的 `game_skills/game_cast/game_skill_receipt` 获取经验；不为测试创建第二身体循环。女神/司灯复用 `team_cases` 去重，由同一 case 汇总多个真实任务的回执、场景和玩家反馈。只在有新证据时交工程师。学习工具可将已验证的前置条件、操作与失败恢复沉淀为可复用技能；不能把一次推断写成强制前置或自动宣称熟练度。

数值候选写明：技能 ID、实际引擎、改动前后字段、依据的多次使用/失败记录、目标指标、反例和回退条件。女神已有 `balance-overrides.json`/`applyBalancePatch` 是旧秘术覆盖层；改变旧 `cost.mana` 不会改变铁魔法的消耗。映射技能应研究原生配置，不能给同一施法再扣一套资源。保留玩家既得进度、装备和历史账本。没有覆盖相应配置的测试计划时，交接具体缺口，不扩大权限或自行改测试基线。

性能候选先采同一场景的 TPS/MSPT、命令/查询频率、模型调用和延迟、实体数及加载区块数，记录样本时间和负载。将服务器卡顿、菜单同步、RCON 延迟、模型等待分别定位；服务 healthy 或重启后暂时变快不是性能收益。优先在已有路径消除重复读取/重复调用，避免另起轮询器或无限缓存过时状态。候选只改一项可归因因素，在独立存档用相同负载比较，并保留未参与调优的场景。

工程师使用 `engineering_status().testPlans` 中覆盖实际路径的固定计划，测试通过的源码哈希须与提交一致。工单记录基线、候选、回执、回退版本和仍未验证的效果。候选提交、实服部署、自然运行收益各自有证据；未启用的工程班次不会因一份文档自动运行。部署使用原管理通道与已授权范围，不通过角色文件访问绕过实际工具边界。
