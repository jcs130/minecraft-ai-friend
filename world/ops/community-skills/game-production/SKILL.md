# 游戏设计与制作

把制作工作理解为：在约束下持续交付可验证的玩家价值。制作人负责决策闭环，不替专业负责人凭主观意见定方案。

## 讨论模式

当用户想探索、评价或推演游戏设计，而不是立即制定生产计划时：

1. 先确认讨论对象、目标玩家、期望体验和当前成熟度。
2. 从核心体验、玩法循环、规则、乐趣、认知和手感中选择最相关的角度。
3. 区分事实、设计假设和个人偏好，直接指出冲突与薄弱前提。
4. 比较少量可行方向，说明玩家价值、代价和验证方式。
5. 保持开放讨论；只有用户需要落地时，才转成范围、排期和负责人。

讨论核心体验、系统、规则、乐趣、UX 或手感时，读取 [references/design-lenses.md](references/design-lenses.md)。这些知识已内置在本技能中，不依赖其他游戏设计技能。

## 最小输入

只收集会改变决策的信息：项目阶段、目标玩家与平台、核心体验、团队与可用产能、截止时间、预算边界、当前版本、关键依赖、已知风险和已有测试证据。

没有数据时使用区间和显式假设；不要用行业平均人月、缓冲比例或固定里程碑定义冒充项目事实。

## 工作流

1. 定义本阶段必须证明的产品假设、生产假设和明确非目标。
2. 检查核心体验、玩法循环、规则、反馈、认知负担和内容需求是否一致。
3. 将体验支柱转成少量可验收交付物，并明确负责人和证据。
4. 识别关键路径、外部依赖、资源冲突、不可逆决定和高传播风险。
5. 比较最小范围、目标范围、降级和延期方案，说明成本与机会损失。
6. 为阶段门定义进入条件、完成条件、未决风险和最终决策人。
7. 在评审后更新决定和下一验证点，删除已失效任务，避免状态表膨胀。

## 落地模式

需要把讨论收敛为制作决策时：

- 明确必须证明的设计假设和非目标；
- 把设计方向转成最小原型、验收证据和停止条件；
- 评估系统、内容、技术、人员、QA 和上线影响；
- 决定保留、修改、删除、延后或拆分。

只选择能改变当前讨论或决策的知识，不做全套理论巡检。

## 关卡生产

- 用关卡 Brief 对齐体验、机制、Metrics、内容预算、性能预算和交付阶段。
- 在高成本美术投入前验证主路径、机制空间、遭遇、可读性和性能风险。
- 关卡变更必须报告对玩法、AI、叙事、美术、音频、灯光、QA 和构建的影响。
- 具体空间方案、Blockout 和 Playtest 进入 `level-design`。

## 输出

讨论阶段输出：核心问题、关键假设、可选方向、主要取舍和验证问题。

落地阶段输出：目标与非目标、事实/假设/约束、产品判断、交付物与证据、关键路径、前三项风险、负责人、下一决策点、范围变化及影响。

## 边界

- 不默认引入 WBS、Scrum、固定站会、风险矩阵或新增状态字段；只在它们能解决已证实问题时采用。
- 市场、法务、发行、LiveOps 和平台认证缺少证据时，列为外部依赖，不编造结论。
- 不能用更多内容、润色或流程掩盖核心玩法、底层规则或技术时序的根因。
