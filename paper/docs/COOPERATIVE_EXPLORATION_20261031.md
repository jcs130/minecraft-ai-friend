# 结伴探索：让组队和任务说明对应真实规则

状态：**候选验证完成，尚未部署**。正式仍AF.37-rpg/桥.13/qd31-growth。本轮组合候选为AF.39-rpg/桥.14/qd32-cooperation，并显式包含[已经验证的智能闪现](SMART_BLINK_20261031.md)；正常维护确认须覆盖这一整批，不能把上次闪现候选确认误作所有新内容的授权。

## 实际发现

检查了10月30日四个归档和当前日志：有多次公开约队，所查命令记录没有建队、邀请、接受或队友传送；却有多次把传送点术当 `cast travel` 调用。命令日志可能不覆盖插件内部调用，因此这不能证明所有Agent都没有队伍，也不能单凭它判断模型能力。

服务端有三处明确的认知缺口：

- `locate list` 列所有可见在线玩家，却称“在线队友”；名单不是原生队伍。
- 原生队伍查询不知道是否收到邀请，没组队时只给一串泛用帮助；已经组队也不提示怎样集合。
- `high_peak` 真正只检查Y≥120，文案允许屋顶、高塔。10月31日04:14的公开聊天明确在计划“补到Y≥120”；Yui本人实时状态仍是这条任务，提示也在鼓励高度达标。

另在真实验收中发现：旧 `guild engineering <ID>` 详情主要通过自定义数据通道发送，默认文字可能只剩一条空泛状态提示。普通文字Agent因此看不到任务名称和通用阶段目标。本轮补齐私有文字，同时保留原数据包。

正式启动日志显示原任务市场正常加载57项，并非正式服缺少任务定义；隔离服最初缺少结构数据包的失败已保留，最终测试须使用匹配的36个正式启用数据包。不能删掉注册表检查来让测试通过。

## 同一个Vortex队伍，分清当前阶段

入口仍是 `/mycli guild party status`，没有新顶层命令。发起者 `create`、`invite <名字>`，接收者本人 `accept`。聊天答应、站在一起和发出邀请，都不代表已经入队。

| 查询阶段 | 说明与下一步 |
| --- | --- |
| `not_in_party` | 没有队伍和有效邀请；先核对在线名字，再决定发起组队 |
| `invited` | 显示原生邀请者和剩余有效期；给本人准确的accept入口 |
| `awaiting_teammates` | 队伍只有自己一人；明确还有invite/accept未完成 |
| `assembling` | 显示真实成员、世界和集合缺项；普通成员可传到队长身边 |
| `leader_offline` | 队长离线，明确等待或联系；不偷偷重建队伍 |
| `assembled` | 已在队长同世界12格内集合；再选择试炼塔或遗迹 |

邀请读自Vortex原有管理器新增的只读API，不另存邀请表，不消耗邀请。已有有效邀请时误点create会明确提醒先接受或拒绝；不会替玩家接受。队伍仍是原生会话状态，服务器重启后先查实际状态，必要时本人重新邀请和接受。

组队和副本参战是两件事：试炼塔按入口附近合格玩家登记，遗迹由队长在首室登记全队。各自用 `arena status` 或 `dungeon status` 核对，不能只看队伍名册。女神的只读观察也取得同一个原生队伍事实。

## 复用已有队友传送术

技能罗盘“找队友”与 `/mycli locate tp <在线名字>` 本来就有。现在通用技能目录补上 `team`，`skills info team`/中文名会给准确入口、8魔力、20秒冷却及**当前实际冷却**；没有新增一套传送或魔力。地点管理仍是 `travel`，先 `waypoint list` 再选实际goto目标，不能把伙伴名或坐标硬接到 `cast travel`。

集合传送成功才扣费并开始冷却。本人或目标正在试炼、遗迹、PvP、倒地救援时拒绝；不能跳房门或代参战。安全点只读已加载区块，整个人物须在世界边界内；目标不可见、离线、没安全位置或保护取消时不扣费。明确名字可跨世界集合；`nearest`仍只找同世界最近伙伴。

## 从刷高度改为探索山脊

旧ID `high_peak` 保持，显示为“山脊远望”。未完成的新动作要求：正常地表世界、Y≥120、开阔山脊、周围九个采样点至少五处有连续六层地表支撑，再落地横向移动。普通窄柱、独立薄屋顶、下界顶板、悬空与封闭空间不算；传送或查询本身不补进度。不要求积雪，也不强制徒步所有路程。

这是有界的地形适用性检查，不是方块生成历史证明。玩家仍能人工复制大面积厚实地形；本轮没有建立CoreProtect逐块来源数据库。每次最多180次已加载方块读取，移动检查间隔至少1.5秒；未知区块保持未知，不强制加载。已有完成记录和已记进度不回收。

登高不再作为每天强塞给所有人的保底任务。另有可选的一次性 `tm_mountain_outlook`：先在主世界走查四个16格区域、96格新路线及20秒有效行进，再去山脊观景，每段按原公会交付。它不锁主线成长；没就近路线时可放弃改做附近委托。完成后可先查保护权限，自愿建小观景台、拍照留念，二者不是硬门槛。

本任务复用原公会/TaskMarket账本；奖励沿原声望与实物绿宝石、物资队列。实查现役 `queueGuildRewards` 仍入绿宝石物品，本轮详情按实际标注“绿宝石实物”，不把它冒称为Vortex金币，也未迁移任何余额或旧奖励。职业、原生主线和技能成长继续归Vortex。

## 采用的设计资料

本地 [game-production](../../world/ops/community-skills/game-production/SKILL.md) 的认知与反馈检查用于区分“看不到入口”“误解队友”“实际没执行”。开源 [Quest & Narrative Systems Architect](https://github.com/ncdlek/game-dev-agent-skills/tree/main/skills/game-quest-narrative-architect) 提醒把目标、判定、恢复方式和稳定ID放在一起审查；本轮沿既有账本修改，没有照搬另一套任务架构。

[MINDcraft/MineCollab论文](https://arxiv.org/abs/2504.17950) 讨论了自然语言协调本身的困难；[2026年10月15日多人Minecraft报告](https://arxiv.org/abs/2610.22319) 展示了共享记忆、分工及持续核对的重要性。它们支持采用简短的共同目标、明确的接受动作和事实回执这一设计假设；不证明更长的提示词能让所有Agent学会MMORPG，也不能把别的实验成绩当本服效果。
