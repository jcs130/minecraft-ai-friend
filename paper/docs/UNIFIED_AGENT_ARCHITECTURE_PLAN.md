# 千灯纪统一智能体架构实施计划

## 目标与范围

每个智能体登记一个稳定的 `characterId`。角色独立拥有姓名、人格、行为偏好、关系、记忆和音色，作为跨身体接续的依据。原生村民、车万女仆、Numen 和 Mineflayer 共用文字、私聊、语音、记忆和决策框架，各自由身体适配器执行游戏动作。村民交易、女仆饰品与背包、玩家权限及模组动作继续由各自的服务器规则处理。

先迁移共享的对话与记忆，再逐步启用身体交接。对话功能可以独立交付，换身须通过身份、动作和资产的一致性验收。部署时只给已登记的智能体开启。普通村民继续使用原生 AI。

~~~mermaid
flowchart LR
    I[原生聊天、SVC 转写、交互、世界事件] --> E[事件归一与权限校验]
    E --> R[按角色送达及判断是否回应]
    C[(角色档案与个人记忆)] <--> R
    R --> D[原生规则、系统一、主模型]
    D --> S[统一文字、私聊与语音投递]
    D --> B[控制权与动作执行]
    B --> V[村民]
    B --> M[车万女仆]
    B --> N[Numen]
    B --> P[Mineflayer]
    S --> A[送达与动作回执]
    B --> A
    A --> C
~~~

## 一、组件归属

| 组件 | 具有什么数据与职责 | 实现落点 |
| --- | --- | --- |
| 角色登记 | `serverId + characterId`、显示名与别名、档案版本、角色归属。一个角色可有多个已登记身体，同一时刻只激活一个。 | 以现有 `NpcCharacterProfile` / `NpcBodyProfile` 候选为起点，登记表增加原生村民、Mineflayer 及各自接入状态。游戏服验证玩家 UUID、实体 UUID 和原生主人。官网显示已核对的状态。 |
| 人格档案 | 角色设定、性格、目标偏好、称呼、对话长短、语言、`voiceProfileId`、决策配置和用量上限。管理员配置与学到的经历分别维护。更换模型供应商保留原人格和历史。 | 现有模型网关、按角色配置及提示词组装。亲密度只影响合适的语气，使用角色关系或已确认的原生好感度。 |
| 事件与对话 | 统一游戏文本、私聊、近聊、ASR、任务与生命周期事件。负责选收件人、对话轮次、是否应答、去重和送达状态。 | 沿用 AgentFriend、VillagerQuests、托管收件和 QiandengVoice 的认证采集。先收敛事件与发件契约，再按角色替换路径。 |
| 决策与执行 | 按角色独立排队。原生 AI 处理寻路和日常动作。系统一决策处理短时、明确、可选项有限的场景。主模型处理社交、计划与歧义。动作按实际能力、最新观察、权限和控制版本核对。 | 复用 HarnessRuntime、BodyPort、动作账本与系统一。DSH 等模型客户端接到决策面。游戏侧适配器执行原生动作。 |
| 记忆与关系 | 每个角色保留亲历事件、所知事实、习得方法和关系。可公开事实经明确发布进入共享世界知识。按权限检索和失效。 | 复用本地 SQLite、热上下文和 Graphiti。Graphiti 作为可重建索引，游戏事实以服务端回执和可追溯事件为准。 |
| 音色与呈现 | 角色音色、语言、语速、音量及授权过的原声资源。按收件范围送文字、气泡和 SVC，统一播报排队。 | 复用 SVC 顺序控制、现有本地或云端 TTS 和气泡插件。原版、基岩和未装 SVC 的客户端可读文本。公开观战只接收允许公开的内容。 |
| 管理与运维 | 角色级状态、开关、暂停、预算、事件与动作查询。各角色的队列和故障恢复独立。 | 托管健康及现有管理入口增量扩展。无需给每个角色起一个模型服务，单个角色的超时或积压由自己的队列消化。 |

统一架构可在一个托管进程运行多个角色。每个角色独立限制排队、在途请求与预算，关闭和重建都在该角色自己的监督任务中执行。统一模型调度计算包括排队在内的总截止时间，给每个角色公平的并发机会。Java 主线程适配器仅做原生状态采样、权限校验及执行。ASR、TTS、模型请求、图查询及持久化等待在工作线程或现有异步进程处理。村民休息、交易以及女仆种田等默认由本地 AI 执行，按事件或必要的短轮次唤醒模型。

## 二、身体能力矩阵

| 身体 | 首批接入能力 | 身体专有能力与限制 |
| --- | --- | --- |
| 原生村民 | 附近文字、点名、角色私聊和角色记忆。使用原生村民的真实位置送附近气泡及可用语音。 | 原生交易、职业工位、作息与村民寻路。战斗、玩家背包、法杖与玩家指令只有完成正式适配才对模型声明。0 玩家名额。 |
| 车万女仆 | 同一对话、音色、角色记忆。保留原生实体身份和自己的背包。 | 随行、护卫、职业工作、装备与饰品按模组和服务器准入。RPG 法术仅公布当前身体真正能放的技能。独立 Youer 已实测装备与移动占用 0 名额。 |
| Numen | 同一对话、音色、角色记忆，按原玩家档案接续角色的已支持动作。 | 通过原生模组接口验证技能、战斗与工作能力。共享相同原玩家存档时，沿用其游戏权限。当前准入实测占用 1 名额。 |
| Mineflayer | 同一角色使用普通游戏连接。聊天、私聊和游戏操作通过现有客户端工具。 | 只有服务器实际开放的原版协议、菜单及技能路径进入动作目录。普通连接占用 1 名额，真人接回走已认证玩家连接。 |

模型上下文包含实时能力清单，例如 `movement`、`inventory`、`combat`、`spell.cast`、`trade`、`work`。原生动作随身体与服端权限自动变化。角色有魔法师的记忆，能否施法仍由当前身体、职业、装备和魔力决定。扩大一类身体的能力时，只需增加适配器、契约测试及配置；首批的原生村民保持自己已经会做的事情。

## 三、文字、语音和私聊

1. **收件。** 游戏侧产生稳定 `eventId`，包含类型、真实发件人、目标角色或原始听众范围、会话 ID、时间、世界、来源和回链。同次麦克风播报产生的最终 ASR 为同一事件，语音识别文本用「语音识别」标记和展示规则发送。模型接收经验证的通道和角色身份。公屏的名字或模拟私聊格式只按正文处理，私聊接收方由游戏服权限确定。已登记的原生村民接入与女仆、Numen 共用的 `/npcsocial <居民名> tell <消息>` 定向私聊入口。
2. **选择谁回答。** 私聊或明确点名优先对应角色。多人点名时，按原目标、当前话轮与现场事实选回应者。普通熟人聊天优先延续最近两轮已确认的会话。人多时环境闲聊默认聆听，附近事件经过距离、维度、对话相关性和预算过滤后再进入角色队列。必须保留合法的「不回复」决定。
3. **防止循环。** 发件记录关联 `rootEventId`、`replyTo` 和 `utteranceId`。角色输出、字幕、观战转发和 SVC 回传保持来源标记，同一角色同一输入最多接受一次模型决策。两个角色恰好说出相同文字时，按各自原消息 ID 收录。显式的 Agent 间对话按会话控制轮流回应、相似回复与自动轮次。建议从最多 2 个连续 Agent 自动回合开始，由新的人类输入、实际动作结果或明确外部事件开启下一轮。周期关怀必须有实际场景变化。
4. **发件。** 回复先绑定一次角色发话回执，再按同一 `utteranceId` 生成文字、气泡和音频。游戏聊天只出现一行逻辑消息，气泡和字幕共用正文。私聊文字和音频只投递给原发件人与确认的接收角色，附近观众和公开转播仅可收到获准的附近消息。默认等当前人类讲话结束再播，播放前复核对象、位置、有效期和角色控制版本。语音稍后不可用时，保留文字送达和明确的语音状态。
5. **声音。** 音色档案随角色，身体只提供发声位置、可用客户端通道和动作反馈。每角色可选固定本机 TTS 或云端语音引用，同档音色用于附近发话、私聊和短战斗语音。原生短句若已有对应音色资源，纳入同一播放队列。没有匹配资源时，用该角色 TTS 或按角色配置静音，避免同一角色随机切成别人的声音。用「已请求合成」「已提交播放」「实际听到」三个证据区分结果。

当前村民仅接受自己的近聊和语音入口，Java 为每位听者保留短历史，模型以单轮对话为主。托管 NPC 已有对话关注和私有收件箱规则。先让两边读写同一事件/回执契约，再接上现有的 SVC 路由。这样能保留任务、交易和真人原版客户端体验，同时逐步替换重复的对话处理。

## 四、记忆范围与角色换身

- **角色记忆。** 用已认证的 `serverId + characterId` 寻址。每条经历附 `eventId`、时间、当时的身体 UUID、世界和事实来源。Minecraft 主世界、末地、下界是同一角色的经历地点。现有分世界的键先做有界映射和逐角色对账。独立服务器继续隔离。
- **人际与私聊。** 私聊正文、好感变化及关系记录按真实参与者分区。同一角色面对不同玩家时读取相应的关系和公开事实。参与者权限在检索前和场景输出前重新校验。公开模型上下文和观战数据只使用对应的公共投影。私聊原始内容进入持久记忆需要明确配置，首批默认短时上下文与必要的最小化事实。原始语音默认不做长期记录。
- **记忆存取。** 把观察到的事实、他人陈述、计划与已完成动作区分开。原始记录以 SQLite 为主，Graphiti 在后台收录适合索引的事件，提供时间和关系检索；远端模型只接收当前回合授权范围内的相关摘要。旧任务回执和当前世界事实优先用于判断。索引异常时维持本地检索，修正或删除之后从索引中同步失效。
- **换身。** 沿用原角色人格、音色与所有有权读取的关系。身体登记携带原生标识、主人和 `generation`。旧身体先暂停、结算在途动作与发声、保存。目标身体核对 UUID、权限、原生数据和能力后准备就绪，再发新控制版本。切换期间的未送达消息按原 `eventId` 继续查回，已过期的附近发话结束；明确授权的私聊可在同一角色收件箱接续。跨玩家和实体的装备转移走单独的资产账本。原生村民的职业、交易和工作站状态随其原实体保存。

代表性验收为同一测试村民记住与两位玩家各自的一条私密经历，再依次使用原生村民、女仆、Numen 或 Mineflayer 测试身体。读回同一个 `characterId`、人格和音色，给出恰当回应，并核对真实允许的动作与原生保存结果。每位玩家只看到与自己有关的对话记忆。

## 五、实施工单与发布门槛

| 阶段 | 交付和依赖 | 必须验收 |
| --- | --- | --- |
| 1 角色登记与诊断 | 以角色为单位梳理现有 NPC、村民、音色、身体和历史记忆来源。登记接口先只读；旧配置迁移用显式角色映射，按保存前像、摘要和可回退版本校验。 | 肥鱼、结衣、桐人及一名测试村民分别能读回正确人格、身体、音色和记忆范围。旧 ID、重复身体与归属冲突可诊断；误配置会明确拒绝。 |
| 2 对话与注意力 | 建统一事件和发件回执。先只记录路由判定，再启用一个测试村民和一个现有身体类型。现有规则继续处理各自玩家和任务入口。 | 实测玩家、女仆与另一村民发话，范围内旁观者可见附近聊天。点名、多人、私聊、假冒系统消息、转写重发和断线均通过。每个接收者对同一原消息最多收到一次。私聊仅授权双方可见，包括文本、声音和记忆，覆盖第三人、同账号另一角色、观战和日志。真人实测听感。 |
| 3 音色和记忆 | 接角色音色目录、SQLite 与 Graphiti。迁移村民的每位听者历史时保留原访问范围、时间和事件身份，原历史由对账工具只读导出。现役托管使用原位置可查回原记忆。 | 四角色实听音色独立，同一角色换身音色一致。断网、语音排队、换维度、Graphiti 休眠和模型超时保持正确的文本与本地记忆；私聊内容不会混入别的关系。 |
| 4 村民、女仆、Numen 和 Mineflayer 身体接入 | 村民先以对话和交易角色工作，再增加经验证的移动或工作动作。按角色开启控制交接，资产独立校验。先用临时身份做测试，再决定对哪些正式角色开放。 | 原生村民 → 女仆 → 原位恢复，及女仆、Numen、Mineflayer 各声明路线成功。检查死亡、未加载、同一角色并发接入、未知回执和服务器重启。女仆常驻零占位、原角色无背包复制、交易状态正确。 |
| 5 灰度与迁移旧入口 | 一名已登记居民先启用，再逐步加入 Numen 与女仆及更多居民。分开记录候选、合并、部署和真实游戏验收。用角色开关回退，相同事件在任一时刻只由一个执行端投递。每种接入通过灰度后移除对应旧消息路由。 | 以同构服务器基线对照 MSPT、队列延迟、ASR/TTS 并发和模型用量。先用 1/5 个角色核验，再测 50 个休眠角色、3 个活跃角色及 20 人突发对话和 24 小时混合运行。休眠角色没有推理开销。注入 SQLite 锁、模型、Graphiti 与 TTS 故障，其余角色可以继续活动，直接私聊能收到回执或明确的繁忙状态。 |

每阶段交付源码、自动回归和对应的隔离实机证据。建议首批把同构负载下的 p95 MSPT 低于 50 ms、相同场景增量不超过 5 ms、重复送达 0、迟到语音与旧身体动作被接受 0 作为压测门槛。若实际基线不允许，记录瓶颈再定玩家数和模型限额。诊断以角色、身体和当前控制版本为维度，能串起 `eventId → decisionId → utteranceId/actionId → receipt`，同时记录没有回答的原因。灰度回退保留最新存档及已写入的回执，读取旧入口时继续核对原请求，遇到结果未知先暂停。

## 本轮起点

候选已把托管角色档案与女仆或 Numen 身体配置分开。在模拟适配器上重启托管并换身，重读了同一角色的原人格和 SQLite 记忆。村民候选允许服务配置指定稳定角色 ID，验证不同听者仍采用不同范围。村民旧历史迁移、统一私聊和实际换身属于后续工单。

真实 Youer 隔离服有两条独立证据。女仆装备铁剑并移动 9.90 格时占用 0 个玩家名额。在另一个仅限显式配对的测试中，原玩家下线后，已加载女仆仍可通过服务端读取该玩家最近一次已保存的 Vortex 等级、经验与职业。两项均为候选验证，写回进度和跨身体资产转移需要另行验收。
