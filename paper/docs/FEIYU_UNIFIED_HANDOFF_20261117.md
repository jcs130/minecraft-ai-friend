## 统一到哪一层了

主干 `90ead3ac` 的 `packages/agent-harness-py` 已有 `BodyAdapter`：身份、能力发现、状态、动作、原请求对账、停止与连接生命周期。`NumenBody` 接服务端托管接口；`MaidBody` 通过主人的已认证游戏连接调用 `mc_maids`。后者还不是主人离线后仍可用的居民端口。

PR [#280](https://github.com/jcs130/minecraft-ai-friend/pull/280) 的原生居民候选提供 `/maidagent resident …` 和同 UUID 的 `ResidentServices`，接现役公会、经济、试炼及 Vortex。它们是统一上层的可复用执行接口，**尚不能把“已有 Python 契约”和“已有居民命令”合称为已经接通并上线的常驻居民 BodyAdapter**。

对调用方应当统一为 `identity / capabilities / snapshot / act / result / stop`。Numen、Mineflayer、私人女仆和居民保留各自真实身体与动作能力；不能把某一种身体没有实现的技能广告给所有身体。Harness 选择、人设、记忆归属和实体生命周期分别管理，换推理框架不创建新身体或新人物。

## 不能直接改配置的原因

1. `MaidBrainControl.bind` 按 UUID 拒绝第二个 active handler。旧肥鱼绑定还在时直接新增 `tlm-maid-agents` 登记会失败；不能删除这条检查。
2. 旧伙伴护卫、驻点巡逻和主人随行会写导航，新居民也会写导航。需要一次明确的控制权交接，旧代次的模型结果和动作必须失效；不是只换模型名。
3. `NativeMaidSpeech.valid` 依赖旧 `sharedDialogueEnabled`。简单禁用旧脑会顺带停掉原 SVC 语音。语音、气泡、原生命恢复和库存访问应保留，决策与移动的拥有者只能一个。
4. 新 `ResidentConfig` 当前强制住房和床位。**接口统一不要求把肥鱼改成公共招募居民**，也不要求搬家、重设职业或赠送装备。优先把原私人伙伴执行器接到统一契约；如使用居民执行器，先支持这类既有伙伴的身份/随行语义，不填虚构住房绕过校验。
5. 旧 `NativeMaidMagicSupport` 的魔力是旧护卫内存池，新居民 Vortex 使用本 UUID 的原生 RPG 资料。若此批同时迁移战斗，必须明确读取哪个池、保留已有 RPG 等级/点数/冷却；不能把两套数值都报成唯一真实值。

3. 验证新旧 CLI/菜单可查询同一个身体；主人继续能正常交谈、指令和查看背包。既有私人跟随关系保持，公共招募默认不增加。
