# 配置占用与副本永久暂停的根因修复

状态：已按本批授权完成180/60/10秒预告、原JVM退出和E/F当前游戏/认证冷备，正常重启上线 **AgentFriend 0.4.47.52-rpg**。后台读取、女神巡检和实际权威状态联读均已核验。

## 为什么会一直“锁住”

有两层问题。Windows 上，读者尚未关闭文件时，替换整个 `config.yml` 可能被拒绝。受控测试中，普通 Python 读者能够复现；即使读者允许删除共享，本机替换已打开目标仍返回拒绝。120秒只读句柄采样未发现持续占用者，没有17:57现场句柄跟踪，不能认定某个具体进程或杀毒软件就是历史故障来源。

更关键的是业务设计：副本和普通功能共用这个大配置文件，却有多种保存路径；一次 I/O 失败被转成持久 `fault`。旧版仅在少数初始阶段自动重试，后续阶段即使文件已释放仍会永久暂停并占住入口。AF.51已经修复“后续失败回退已保存房间”的问题，但有限次数重试并不能解决这一耦合。

## AF.52 改了什么

所有普通 `saveConfig()` 和副本事务统一使用一个写入器及递增版本。完整状态先在私有目录写入并强制刷新；正常情况仍直接发布 `config.yml`。Windows拒绝替换时，保留不可变 `.state` 文件并写入带版本、大小、原快照摘要和完整校验的提交记录。明确提交后才接受本次状态；`config.yml` 此时只是待更新快照。

后台退避只重新发布已经提交的相同字节，不重新调用房间结算、领奖、传送或其他游戏逻辑。重启前先恢复最高有效提交，随后才启动玩法管理器。无法确认提交、记录冲突或数据损坏时仍停止相关保存并保留现场，不能自动删除证据或凭日志补奖。一个原子配置提交不等于Minecraft世界、物品和所有第三方数据库的跨系统事务。

经过类型确认的存储故障有独立标记。原队伍回到原遗迹后，系统在有限退避内核对并恢复已保存阶段；未知原因不会仅凭 `data_unavailable` 字样自动解锁。原有 `/mycli dungeon resume` 保留；状态说明增加回场恢复指引，没有增加玩家命令。

## 读取、观测和备份

网站活动投影通过只读 `agentfriend_state.py` 读取最新完整提交；Windows句柄尽早关闭，再解析YAML。共享删除标志是减少干扰的措施，不是“文件打开时一定可以替换”的保证。女神继续使用原45秒快照预算和固定查询，在现有副本审计中获得 `stateStore`：

| 状态 | 含义及下一步 |
| --- | --- |
| `published` | 已提交状态与快照一致；其他玩法仍需各自验收。 |
| `projection_delayed` | 游戏提交已保存，只是快照延迟；不要要求重打、重领、重开。 |
| `commit_unknown` | 保留原记录并核对原场次、物品及奖励；不要盲目重试。 |
| 未提供 | 旧版没有该观测信息，不能推断为正常。 |

必须备份整个 AgentFriend 数据目录，包括 `.state-pending` 的 `.state`、提交JSON和锁文件。它不是缓存垃圾，不可只备份旧 `config.yml` 或按临时文件清理。发布维护仍使用正常停服的一致冷备。待发布时不要手改快照；重启发现与原快照不一致会保留冲突并拒绝猜测性覆盖。
