# 女仆生命状态持久化候选 · 2026-11-07

状态：**0.1.8-life 候选，尚未部署**。正式服继续使用 0.1.7-agent；这次工作只涉及源码、合成数据隔离服和回归测试，没有重新启动正式服，也没有再次复活或操作真实女仆。

## 问题与修复边界

旧版 `NativeMaidAgentSupport.enrich()` 在加载到原女仆时返回 alive，却没有保存这个见证。原墓碑因保留遗物而继续存在，女仆卸载后查询又读取旧死亡记录，导致同一死亡重新出现。隔离服已复现，正常重启后也能复现；这是服务端状态合并问题，不能只靠客户端忽略提示解决。

新增 `MaidLifeEpisodes` 管理同一主人与女仆 UUID 的生命周期。原生实体加载、本人查询和已有五秒巡检提供正向存活证据；没有新增世界扫描、强制加载区块或动作循环。原生死亡事件确认新的死亡，未取消且实际死亡后才入账；原生墓碑可补充位置与遗物标识。再次见到原 UUID 存活时解决上一死亡事件，并先保存恢复记录，再通知主人。

| 情况 | 返回 |
| --- | --- |
| 原生实体确实存活 | `alive`，可附历史死亡及恢复观察 |
| 曾确认复活，现未加载，旧墓碑仍有遗物 | `unloaded_or_unavailable`，`historicalDeath`，不返回当前 `death` |
| 新的原生死亡，或在最近存活见证之后出现的新墓碑 | `dead` 和新的 `death` 事件 |
| 旧版只有墓碑记录，没有可信的近期存活/死亡见证 | 保留历史证据，当前状态未知；靠近最后地点查询 |

`observedAt` 只表示再次见到原 UUID 存活的时间，`actualRevivalTimeKnown:false`；不从两次查询间隔猜测实际复活时间。死亡、恢复事件使用稳定的48字符以内 ID。同连接去重，重连补告；客户端应持久去重并把事实交给原主人格，不能据此自动执行复活或物品写操作。详细字段见[命令协议](../integrations/touhou-maids/agent/CONTRACT.md)。

## 保存与失败处理

沿用 `native-lifecycle.json` 和原 `ReceiptJournal` 保存方式，保留旧 UUID 顶层记录，在 `_episodes` 下增加 `ownerUUID/maidUUID` 的 schema 2 元数据。旧墓碑不会删除，主人变化也不会把前主人的事件交给新主人。存活心跳最多每30秒保存一次，死亡和恢复立即保存。

保存失败时保留待写状态、最多每30秒记录一次警告；恢复观察返回 `persisted:false`，不签发持久化恢复提醒。后续成功保存后才允许提醒。损坏文件不自动清空或重建。代码回退应保留当前账本，不能回灌旧账本、世界、墓碑或玩家物品；旧版不理解新增的分期状态，回退后会重新暴露旧问题。

## 隔离验证与复现方法

只使用新建 localhost 世界、合成玩家和随机女仆 UUID，不复制真实存档、密码、模型密钥或聊天数据。`lifecycle-stage.mjs` 强制核对新测试服标记及25938/25939端口；它在测试世界执行死亡和同 UUID 重新生成以验证身份与状态边界，**不代表已经测试原生祭坛复活操作**。

1. 0.1.7：死亡→保留墓碑其他物品→同 UUID 存活→卸载。10项中4项失败；重启后2项中1项失败，确认旧墓碑被重新当作当前死亡。
2. 0.1.8-life：相同流程10项通过，正常重启及第二次死亡8项通过。测试 JVM 均正常停止；旧墓碑剩余2栈物品的类型化 NBT 摘要在恢复、卸载、重启与第二次死亡后均保持。
3. 纯 Java 生命周期回归29项：包括旧账本迁移、保存/重开、重复事件、第二次死亡、延迟墓碑、同秒恢复、不同主人、未来时间与输出隔离。
4. 可选宿主适配器5项通过，覆盖恢复事件、状态查询和不重放写操作；GitHub CI 直接编译并运行实际 reducer，Gson 依赖固定 SHA256。

源码、基线和候选摘要以及各阶段结果见[候选清单](../manifests/maid-lifecycle-candidate-20261107.json)。最初两次测试准备分别遇到合成物品数量错误和 RCON 长 NBT 截断，修正夹具后才记录上述旧版失败；准备失败没有计入缺陷复现或通过数量。
