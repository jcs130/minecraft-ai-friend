- 解散生命周期复现与已验证修复：[上游 Issue #163](https://github.com/Dwinovo/minecraft-numen/issues/163)。用连接的正常 `onDisconnect(DisconnectionDetails)` 路径代替直接移除；保留身份检查、移除事件和 `LEAVING` 的 `try/finally`，不吞掉链接异常。

## 游戏语音

外部客户端已生成 WAV，但游戏返回 `VOICE_AUDIO_UNAVAILABLE_QUERY_STATUS`。服务端证据定位到媒体监督器使用无音频依赖的基础 Python；进程在 `import sherpa_onnx` 时退出，HTTP 音频准备入口没有启动。这发生在 Opus 播放之前，不能用客户端生成成功代替游戏实播成功。

监督器改用现有语音虚拟环境，并在启动循环前核对 `numpy`、`scipy.signal`、`sherpa_onnx`。依赖错误直接停止，不持续制造失败日志。Windows 虚拟环境会启动基础解释器子进程，接管时同时校验其真实父进程、两条完整启动命令、脚本及私有配置路径；兼容 Windows PowerShell 5.1 附加的尾部空格，不按进程名接管其他 Python。

已完成：

- 11 项 Python 媒体回归和 11 项客户端请求/终态回归。
- 8 项真实 Windows 虚拟环境身份检查；无父进程、错误配置/脚本/解释器均被拒绝。
- 与失败上传相同采样率、声道、时长和字节长度的合成 WAV，经隔离及正式 HTTP 路径由 44.1 kHz 转为 48 kHz 单声道。
- 正式 CPU ASR 已加载；守护程序重启后正确接管原媒体进程，保持就绪。
- 原失败请求仍为原先的 `queued → failed`，编号、时间、指纹不变，没有重播或伪改成功。TTS、系统一和游戏服务不因这次媒体修复重启。
- 当前内核隔离服的全新合成音频经过上传、转换、Opus 编码与 SVC 分发，附近监听收到 368 包、远处为 0；同号重复提交只返回原回执，音频包数不增加。此项是服务端链路检查，不是独立 Java 客户端录音。

这证明服务端音频准备恢复，**尚不证明可米原测试句已在独立 Java 客户端被听到或录到**。原句不重播；后续实播须用新测试句、新请求 ID，并保存独立录音证据。真人麦克风到附近字幕的端到端验收也单独记录。
