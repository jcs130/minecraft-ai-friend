## 本轮更改

1. Numen 的单人委托、遗迹查询、装备和箭矢准备、地形调查按身体可用工具提供。固定搭档只影响需要搭档的队伍操作。向模型暴露的队伍子操作与执行器检查共用同一套规则。冒险动作仍须角色工具许可，真实 RPG 指令继续经过具名账号权限检查。原组队、委托和原请求回读继续走既有流程。
2. Python 和 TypeScript 身体适配器统一按原请求 ID、动作名和参数核对回执。相同请求并发提交只发一次。改参或收到别单回执时给出冲突或待核对状态。先到的原生终态保留。此保证覆盖适配器实例的回执保留期，跨进程继续使用现有持久化账本和原请求查询。

Python 共 556 项通过，2 项因缺少 Harness² 专用环境跳过。TypeScript 11 个文件 94 项通过，类型检查通过。Minecraft Agent 核心源码、运行时构建和类型声明也通过校验。测试使用本地候选，真实动作证据沿用上表标明的正式观察与隔离记录。

## 后续重构顺序

1. **适配器声明能力。** 统一结构含动作 ID、实际支持的参数、前置条件和完成凭据。Numen 映射原生技能和玩家指令，女仆映射原生任务和附属模组，Mineflayer 映射客户端工具，村民只公布实装的对话和工作。保留能力参数表和实测用例，新增身体通过注册接入，避免每次改共享规划、观察和派发代码。
2. **按角色授予权限。** 计划器只收到当前身体支持、角色获准且现场可执行的动作。区分「身体不支持」「角色无权」「现场条件缺失」「可执行」，同时给出下一步。角色档案只负责个性和行为偏好。角色选搭档不影响单人准备，定时复核不影响战斗和资源调用。
3. **以原生结果验收。** 位置变化确认到达，库存增减确认交付，命中事件确认参战，原发件人和收件人确认送达。断线、迟到、超时及重启用原请求 ID 查询。更换身体前要看到旧租约撤销、物理行动停止和数据已保存，再开放新端。
4. **从真实混合场景验收。** 选测试村民、女仆与 Numen，分开验证三种原生动作和同一对话能力，再接入原版 Mineflayer 与千灯纪客户端对照。加入队友会合和副本、跨维、满背包、进程重启、真实讲话与私聊隔离。关闭、数据库锁和慢模型按角色隔离，记录健康与动作仍在更新的证据。候选、代码合并、正式加载和实机效果分别记录。
