## 本轮修复

1. 移除“住宅维度就是唯一可行动维度”的错误假设。普通局部坐标仍是身体当前维度的绝对方块坐标，`home` 独立使用登记的住宅维度。
2. 自动随行的传送冷却现在是有间隔的等待状态。此前错误状态会让 NPC 永久停在原维度；现在冷却结束后继续同一已同意的跟随关系。
3. 传送前保存原请求、来源、目标与契约；跨维度之后按同一 UUID 找真实实体，不重新生成角色。只有实际到达才扣 5 魔力并进入 60 秒冷却。断电/未知结果禁止自动重放，可用 `travel-receipt` 查原请求。
4. 模型可使用 `act` 提交原生技能和换装；收到的是本人真实物品槽位、技能效果和冷却。同行时不能用任意移动命令抢走领队的跟随控制，工作模式才允许局部走路/挖建。
5. `walk` 使用临时原生导航锚点，解决原居家日程把 NPC 拉回、导致合法行走超时的问题。永久住宅不变；夜间恢复真实床位，队伍撤约回原住处。
6. 仅正在执行的 `photo take` 持有导航；不设置 `NoAI`、不永久坐下、不冻结 `photo status` 等查询。任务失败/结束后释放，未知相机任务仍查原回执，不重拍消费。
7. 职业冷却改用服务器统一游戏时间。升级旧数据时保留剩余冷却，不因跨维度时钟差异额外恢复魔力。
8. 夜间回家和自主规划也尊重未核对的传送；已拒绝请求保持有界重试间隔，不按 tick 反复创建动作。读取别的维度的住宅不会在当前世界强制读取同坐标区块。
9. 线上施法复验暴露对话/动作的记忆文件冲突：聊天答应与实际动作共用请求 UUID，不能写同一不可覆写文件。现在动作使用稳定的独立证据 ID，同时保留 `sourceRequestId` 指向原动作；不改旧对话。记忆工作器也检索本人实际动作，不能只检索对话对象，使本地和 PowerContext 后续都能区分承诺与真实结果。
10. 模型还出现过沿用上一轮“仍在冷却”的对白。当前观察增加依据真实魔力/冷却计算的 `resourceReady`，并从对话上下文去除重复原始背包、家具计划与旧动作回执。此字段只说明资源条件，不代表已经找到合法目标或施法成功；历史对白不作为当前计时来源。

## 验证方法与证据

本轮使用真实 Youer/NeoForge/TLM 实体、独立端口和带标记的 QA 世界。可重复的行为测试使用固定模型返回以隔离身体执行逻辑；线上模型测试另列，不混称全部为自主决策。

- Java 契约/账本回归：47 + 46 项通过。
- Python Qwen Code 适配：8 项通过。
- MC 核心本地/PowerContext 记忆回归：4 项通过，包括同一对话的独立动作证据与本人回忆。
- 三 NPC + 隐藏原生 Java 客户端的多维度场景：36 项通过；构建归属见本批清单，不把早一构建的测试改写为最终摘要。
- NPC 领队原生行走、随行跨维度、未知传送不重放：11 项；独立原始物品/技能/回执检查另 10 项（包含资源就绪与真实魔力/冷却一致）。
- 两处真实艾因格朗特地形住房：17 项；导航锚点修正后再做穿门、夜间入睡及冷重启 9 项。
- 最终线上 Qwen Code → LiteLLM → 原生游侠技能：7 项通过。模型实际选择 `cast sprint`，本体扣除 5 魔力、进入冷却，对话与实际结果分别入记忆，不占玩家槽。这是一次有明确请求的模型动作闭环，不是长时间完全自主生活或耳听验收。

住房初试碰到草占用了门牌位，预检按设计拒绝，改选空位后才安装。NPC 领队初试被原住宅导航拉回，属于真实缺陷，保留失败记录并修复后复验。最初使用 Essentials 的 `tp` 别名、缺少模型素材相对路径、Qwen 预览版能力字段形状错误也有夹具失败，未当成服务器成功记录。一次线上动作没有提供日文副本，不能把中文回复和 `not_configured` 称为日语或耳听验收。旧中断/失败回执不改写为成功。

## 投放与兼容

初始世界使用 `minecraft:aincrad`；这是家和出生点，并不是可传送维度白名单。不要把测试用合成 UUID 写进正式服。旧居民配置缺少 `roamingWork` 时仍为 `false`，不悄悄给现有 NPC 开新挖建权限。按角色配置后，普通领地和原生事件检查依然执行。

住房候选见 [两处房屋方案](../integrations/touhou-maids/standalone/examples/aincrad-neighbors-housing.json)。部署前重查当前房屋占用、原个人领地、独立记忆 Scope、模型摘要和任务物资；只布置空位，不改主世界旧设施，也不替换肥鱼、可米或鸣人。回退只换代码和配置，不回灌世界、身份、物品、认证、契约或动作账本。

本轮没有发布新居民或重启游戏。仍有上述功能/跨端缺口，因此没有把“完整需求全部测试通过”作为投放结论。正式版本和候选版本必须分开记录。

运维注意：`travel-receipt` 可以核对中断的同行传送，但本版尚未提供独立的“核对后解除传送暂停”命令；现有 `acknowledge-unknown` 只处理居民动作账本，不能用于另一份同行传送账本。遇到这种状态应保留原请求并交运维检查，不能删除标记、改成功或另起身体来绕过。这也是大规模投放前的待补项。
