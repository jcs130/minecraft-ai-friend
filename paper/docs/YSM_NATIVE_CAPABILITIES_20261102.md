# 原生 YSM 通道识别与切服握手

**11:23 状态：OptionalPayloadGuard 0.1.1 已加载，但原生模型验收尚未通过。** LoginGuard 0.1.10、原版 YSM 2.6.5 / 协议 2.6.0 保持。正常重连仅涉及登录后台，游戏进程未重启；72份原账号身份与凭据字段保持，E/F 使用 SQLite 一致备份。一次性激活入口已消费，不能重放。

## 正式联测发现的第二个边界

原本的 NeoForge 测试证明了通道识别缺失，但不能覆盖所有客户端的切服行为。正式相机的原版 Fabric YSM 在登录阶段就将物理连接标为协议就绪；切换到游戏后台后，客户端继续显示就绪，游戏后台却一直为 false。24次登录前只读采样确认了这个差异，未写原版就绪属性或修改客户端网络。

0.1.2 候选在保护层保留同一客户端真正发送的七字节版本确认，在该玩家进入配置中的 `paper` 后台后，通过其实际当前连接转交一次。不合成确认，不中转模型选择、动作或任意扩展消息，不授予登录、OP或解码能力。原始消息的转发结果不变；后端来源、目标玩家不匹配、其他版本及已处理消息均不接受。缓存以物理 Player 对象隔离，最多512连接，断线清除；每条实际后端连接最多两次发送尝试，成功后不再转交，旧连接任务不得发送到新连接。

候选与正式状态必须分别记录；下面的首轮测试是 0.1.1 的原始证据，不等于已修复正式相机或远端人物画面。

真实 Fabric 对照使用与正式相同的原版2.6.5客户端、Intel/Mesa运行时和独立账号：0.1.1下客户端原生标志true，游戏后台false；0.1.2下双方均true，游戏实际读回本人无人机选择，新的缓存由16份/5,977,515字节增加为43份/23,998,090字节。客户端没有本地强制绑定，测试角色正常停留35秒后退出，隔离服务器正常停止并恢复配置。首轮测试因没有使用相机专用核显运行时而被既有显卡门禁拒绝，失败回执保留，未放宽该门禁。

## 原因与最小改动

真实原生 NeoForge 观战已能稳定通过认证并保持 OP，但显示普通皮肤。正式只读查询确认可米仍选择 `cormy-winefox-cream/cormy-cream`，外观未停用，且与 live 同世界、同位置；原生适配器却把 live / ag_PhotoLens 的 `nativeDecoderReady` 发布为 false。

隔离观测找到原因：原版客户端通过 `neoforge:register` 发送 3175 字节的原生通道声明。保护层 0.1.0 只识别 `minecraft:register`、`c:register`，因此正常 YSM 消息在发送监测 LOWEST 阶段尚未取消，到 MONITOR 阶段已被过滤。

**首轮0.1.1只更新通道识别。** 按固定 NeoForge 21.1.252 的 `ModdedNetworkQueryPayload` / `ModdedNetworkQueryComponent` 编码读取客户端声明，只认可 PLAY 中的客户端方向或双向接收能力。配置阶段、服务端方向、错误字段、截断或超限声明不能授予 PLAY 接收能力；保留物理连接隔离与断线清除。声明只是解码能力，不是登录或权限证明。

不改原版 YSM、登录规则或模型内容，不设置就绪属性或伪造回应。曾尝试的“认证场景推迟问候”在首轮 NeoForge 测试中不是必要条件，已从发布源码移除；不要安装私有 LoginGuard 0.1.11 实验包。后续 Fabric 实证单独验证真实确认的切服衔接。

协议依据为固定原版二进制的实际编解码和 [NeoForge 1.21.1 官方载荷说明](https://docs.neoforged.net/docs/1.21.1/networking/payload/)；代理消息边界参照 [Velocity 官方说明](https://docs.papermc.io/velocity/dev/plugin-messaging/)。

## 实测结果

| 隔离组合 | 登录与原女仆查询 | 游戏服 YSM 就绪 | 模型资源 |
| --- | --- | --- | --- |
| 正式 Guard 0.1.10 + 旧保护层 0.1.0 | 正常，OP保持35秒 | false | 仅177字节缓存索引 |
| 仅调整问候 + 旧保护层 | 正常 | false | 仍无下载 |
| 正式 Guard 0.1.10 + 新保护层0.1.1 | 正常，OP保持35秒 | true | 原版客户端形成28份缓存文件，约18MB |

最终组合里，测试角色通过本人 `/appearance set qd_observer_drone default` 选择原创 CC0 模型；服务端实际读回模型、贴图、原生就绪及公开网页资源，mandatory=false。所有角色和路径均为独立 loopback QA，未改正式人物。客户端没有强制本地绑定，没有网络或注册表补丁。

缓存核验也纠正了早先的观察口径：本版实际资源位于 `cache/client` 并有 `server_index`，仅查看空的 `cache/server` 目录不足以判断传输失败。上述结果同时核对了真实传输、缓存增量及原生就绪，仍不代替正式远端完整人物画面验收。

70项能力边界检查、真实3175字节原生声明解析、原版客户端联机通过。CI加入无网络能力边界回归。早先测试环境的旧 NanoLimbo分流、Via版本映射和旧日志就绪误判均有失败回执；有效对照统一隔离旧提供者、采用准确的测试端口映射及独立新日志，正常停止并恢复隔离配置。这些测试调整没有改动正式路由。
