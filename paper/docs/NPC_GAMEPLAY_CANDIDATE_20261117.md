# 智能居民玩法闭环候选，暂不发布

这是居民扩展 0.3.8 / AgentFriend 0.4.47.86-npc-gameplay 的开发验收记录。用户已授权全部验收通过后自主合并上线，无需再次询问；完整 CLI、跨端与长期多体等条件尚未全部通过时，仍保留候选。本轮没有替换正式 JAR、重启正式服、生成正式居民或改写正式记忆。

另有原生权限桥 0.1.40-resident-permissions 与相机客户端 0.2.1 候选。权限桥基于现场 0.1.39-spell-policy 的摘要校验构建，只替换权限类及版本字段，不覆盖同包较新的语音/法术类。对应构建和检查归属见 [manifest](../manifests/npc-gameplay-candidate-20261117.json)。这是候选开发分支，不能直接执行历史维护脚本投放。

## 本轮补齐的业务能力

原生女仆是独立的参赛和财产主体。`ResidentCli` 将普通业务服务接到她自己的 UUID、真实女仆背包、装备与有限魔力；没有客户端连接、OP、玩家名额，也不借用创建者或队长的身份。

- `status` 读取实际身体、位置、装备、背包、职业资源；连续查询不递归嵌套旧状态。
- 公会加入、任务发现、接取、核验、交付、放弃沿用原业务规则；领取回执比较实际前后状态，接取不等于任务完成。
- 回收报价及成交、个人金币余额、购买、个人奖励箱存取沿用现有经济账本。默认女仆背包只有实际可用的 6 格，不能把锁定的扩展槽当空位，已装备物品不属于可回收背包槽。
- `arena stash collect` 将既有待领取奖励装入本人的个人箱；箱满的部分保留队列。`list/inventory/summary/take/putslot` 可直接使用；按实际转移量回执，不打开一个 NPC 无法点击的 GUI。
- `land here/list/info/members/trust/untrust` 以 NPC 本人身份执行。没有领地主人权限就不能授权他人。原生传送显式核对本人 WorldGuard 出入权限，不依赖只有真实玩家才会触发的传送监听器。
- 试炼塔和遗迹地下城将登记居民纳入附近参赛名单、目标选择、真实伤害贡献、倒地救援与个人奖励。远处未参赛居民不能领奖，重复领取不重复发奖。
- 伤害达到致命值时按场次进入倒地/救援流程，保留原实体和装备；倒地不能继续派发动作。不会生成替代身体继续假装完成旧动作。
- NPC 在遗迹中的实际战斗贡献进入既有耐久战斗账本，再按累计值投影到本人 `combatXp`；重连不重复加分。原生劳动/施法经验保留为 `workXp`。真人 Vortex 玩家经验路径不额外发放第二份经验。
- 原生种田仅在成熟作物实际被收获后增加 `workXp`，选择工作模式、未成熟和被保护拒绝都不算。收获/补种沿用本人公会账本；女仆提前补种只保存同次任务、本人收获地点、紧邻配对阶段的实际证据，不能将别人的工作算给她，也不会自动领奖。
- 常驻身体当前区块使用 NeoForge 原生运算 ticket；没有真人连接时作物仍按游戏规则生长。只覆盖当前区块，离开的 ticket 三秒过期，不提高正式 `randomTickSpeed`、不伪造连接、不替换自然生长为固定掉物。
- 原生 TLM 世界权限桥识别登记居民 UUID；普通宠物女仆沿用主人权限。驻民不能借用创建者权限，登记或权限模块异常时不放行。原生破坏/放置事件依旧有最终否决权。
- 购买成功明确标记商品仍在待领取队列；收集到个人箱与取到实际背包分别回执。公会验收未通过不会返回成功；限流保留真实原因、等待毫秒和安全查询，旧请求重读不重新成交。
- 相机可确认真实女仆实体和原生/YSM 模型就绪，并沿原 ImageFrame 上传、本人相册与个人奖励箱流程出片。拍照导航持有结束后可实际行走；没有用合成 PNG 代替原生客户端渲染。

这仍是 `resident_classes_v1` 职业曲线，不能描述成已经完整迁移 Vortex 的全部玩家技能。候选发现目录只列出已接到实际执行器的命令，不允许任意控制台命令作为兜底。

## 动作、断线与记忆

### 查询契约与共享核心目标

`ResidentCliContract` 统一提供发现目录、执行回执和历史行动摘要的效果分类。回执新增 `operation`、`queryOnly`、`operationEffect`、`completionScope`。例如 `arena entrance` 返回 `read_only` / `query_snapshot_not_world_action`，附带“只查入口、不移动、不报名”的说明及 `nextSafeRead=arena status`。查询成功仍使用既有 `completed` 状态，旧字段和调用方式保留；目标完成须另核实际坐标、参赛状态等事实。不得把入口查询改成隐式传送。报价也是查询；验收、成交、购买、存取等保持各自实际写操作语义和原权限。

历史执行器接受、但尚未完成居民端验收的附加子命令只补充回执分类，不自动进入能力发现目录。

AgentFriend `.86` 与居民扩展 `0.3.8` 是同一候选组合，发布和回退须作为一组处理。新的业务执行器会先读取居民端 `cliContract`；旧居民 JAR 没有该接口时，不派发这笔业务动作，不能将只升级一侧当作兼容部署。正常查询/动作的原命令与状态字段保留，新增效果字段可供旧调用方忽略；`completed` 仍只代表该操作终态，不代表整个目标完成。未配置 `goalsDirectory` 时不启用核心目标投影，原本地记忆和原生工作保持原路径。

`companion-memory.mjs` 可选 `goalsDirectory` 指向已有 MC 核心 `GoalCheckpointBook` 目录（通常是该运行时数据目录下的 `minecraft-goals`）。每名 NPC 使用固定 Scope：`realm=<世界标识>`、`account=npc:<身体UUID>`、`agent=<身体UUID>`；切换 harness 或模型不能改成另一个人的 Scope。每轮同步读取原核心校验过的目标，发布到本人 journal 目录的 `core-goals.json`，自主决策据此继续目标。未配置时保持原行为。

这条接口是共享目标的只读投影，不是第二套目标引擎，也不自动把行动标成目标成功。上层运行时仍用原核心接口建立、更新和核验计划。恢复的目标仅表示意图；旧库存/位置验证会由核心丢弃，host judgment 是有原时间的历史判断，必须结合实际回执。投影有 24 KiB 上限，错误、串 Scope、时间异常和五分钟未更新都有明确拒绝；不截断成一个更弱的目标。目标读取失败会形成可按原 requestId 查询的失败回执，不调用模型、不扣模型失败额度、不重放身体动作，原生工作和管理员已授权的身体操作不因此被关闭。

### 私人通知的完整记录

真实连续任务发现旧写入端的 `game_notice` 有 `maidId` / `speakerId` 和正文，却漏了记录 `id`，导致持续记忆导入退出。0.3.7 起在 journal 写入边界补齐规范 envelope，并拒绝冲突的身体/记录 ID 与缺失发言者。旧文件保持不变；只有“本人、私人、game_notice、有效原时间、缺失 id”的精确旧格式，才在读取投影中采用原文件名的 UUID，并标注 `legacyEnvelopeRecovered`。别人的通知、损坏时间、其他事件及冲突 ID 都不按此规则修正。

一次 0.3.6 的真实定时自主任务用了 13 轮完成交付、回收、购买与取物，但同步器因上述缺陷退出，因此该组整体验收失败；不能只引用目标成功。原始失败保留。修复后用该批真实原文件恢复 7 条未导入记录，总计 14 条；原通知摘要保持、再次导入 0 条，并按本人 Scope 从核心记忆 API 读取到该通知。后续新版复验及各自构建摘要见 manifest。

线上验收增加 `--scheduled`（仅观察服务器定时器，不手动调用 `plan`）与 `--core-goal`（目标来自共享核心，不塞进人设）。目标判定必须同时具备本人的实际交付、铁剑成交、食物购买、购买后成功取物回执及实际食物增量；已有食物、武器购买或仍在队列里的商品均不算完成。`resident-core-goals-stage.mjs` 只供有专用标记的环回隔离服准备/持续投影目标，正常结束会同步最后记录，不发送游戏动作。

每笔写操作先保存原 requestId，再调用服务。完成回执不可被之后的楼层提示覆盖。异步受理和成功是不同状态；发生写后异常时保留 `unknown` 和身体阻塞，不能自动重放。

未知传送须先查原请求与实际维度/坐标。管理员使用 `travel-inspect` 提供原请求、独立核对 ID、准确的实际位置和说明，核对通过后身体保持暂停；再明确 `travel-resume`。原始未知回执不会被改写成成功，恢复也不执行旧传送。普通 CLI 未确认请求的核对同时解除对应业务阻塞，不能只清外层标记。

较长的结果和私有任务通知进入本人原始 journal。记忆导入使用有界摘要，注明原文件、原请求、摘要哈希和截断状态；完整证据仍保留。重复导入、Scope 隔离、远端故障和后续事件不被大结果阻塞均有回归。

## 已验收与发布门槛

### 本次续验结果

0.3.8 的真实隔离服完成 48 项业务、14 项推理故障、7 项故障冷重启、12 项目标异常、2 项业务冷重启及 2 项目标失败回执冷重启检查。最后仅收紧发现目录的构建与前一构建只差 `ResidentCliContract` 类；对最终 JAR 又验证了 12 项目标异常/恢复与 3 项真实契约检查。各组保留各自摘要，不能将前一构建的全部检查改记到最终 JAR。当前源码独立回归为 Java 215 项、Node 记忆 10 项、Python 网关/目标判定 18 项；相机等较早组别另列。

定时自主对照中，仅将任务放在人设里的版本 14 轮后未完成补给，中途转接了其他委托；这一失败保留。共享核心目标的两组均在 13 轮完成真实目标，但第一组遇到上面的通知导入错误，第二组暴露 QA 工具关闭时 stdin 仍持有进程的问题，均未掩盖原运行失败。第二组在通知修复后产生的 14 条原始记录全部有规范身份；修复 QA 关闭逻辑后，使用同一组原始数据复验启动、同步、正常退出，进程退出码 0、14 条全部导入、原目标存档摘要保持。该补验没有重跑游戏动作或再次消费物品。

最终构建的一次复测在第 13 轮取出 8 块牛排时，验收立即读取背包却为空；第 14 轮实读已出现 7 块。原测试未关联后续库存，错误判为未完成，失败记录保留。原生 `MaidWorkMealTask` 会将整堆食物移到手上再进食；独立隔离复现实际观察到了手持牛排与余量 7 块回包，未禁用或修改进食 AI，正常停服退出。验收现仅在已确认取物后，最多追加 8 秒只读库存复核，并逐次记录采集时间；未确认的取物不触发，绝不重放取物动作。后续正常状态读取也可补足同一笔已确认转移的实际库存证据，新购买会清除旧转移证据。队列、已有食物或未知结果仍不能算完成。


最后使用相同最终 JAR 的全新隔离世界完成整组联测：定时线上模型 13 轮达成真实目标，随后 48 项业务和 2 项冷重启通过；整个启动器退出码 0。14 条实际行动/通知全部按原 Scope 导入，原生记录身份完整，目标投影进程正常结束。原失败组仍逐一保留，这一成功样本不代表长期多体成功率。

这证明一个有明确目标的有限任务链和相应恢复路径；仍不等于居民能自行建立/核验任意长期目标、完整使用所有玩家玩法或所有客户端表现已验收。因此当前 `releaseReady=false`，正式服保持原构建。用户无需再为已授权的正常发布重复确认；先补齐剩余条件。

### 推理故障恢复

线上试验发现的重复失败不能只靠测试器停止来处理。0.3.4 将每个居民的推理失败次数、原请求和重试间隔保存到 `world/data/tlm-resident-planning/<UUID>.json`。失败、非法 JSON 与超时的终态也写入原 `tlm-resident-actions` 账本；执行后来的动作、换框架或重启，不应让原失败回执消失。

间隔从配置的 `planningSeconds` 开始倍增，附加退避上限为五分钟；原配置若更长仍遵守原间隔。`status.planning` 提供 `retryAfterMs`、失败次数和原请求，提前调用 `plan` 明确返回 `model_backoff_no_action`，不会再次请求模型。合法决策通过契约校验后恢复正常间隔；普通领地拒绝或背包不足不是模型故障。此机制不停止原生寻路、睡觉、工作或玩家已授权的身体操作，不降低任何权限与未知动作门禁。

失败注入验收使用合成 HTTP 503 / 非法 JSON / 合法只读响应，检查真实原生身体及冷重启；它只证明故障恢复和执行链，不证明模型自主规划能力。原线上目标漂移、模型超时结果仍保留，不能被这些确定性测试覆盖为成功。

0.3.4 的隔离服实际完成推理故障 14 项、故障冷重启 7 项、普通业务复测 46 项、业务冷重启 2 项。原子记录/故障退避的独立回归另有 21 项。用于复现的 `resident-planning-stage.py` 提供 `Fixture`、`first_run`、`after_restart`：测试启动器将合成 LLM 绑在环回地址，分别在正常停服重启前后调用两阶段函数；脚本会拒绝没有专用标记或非环回的游戏实例。生产故障状态不能靠删除文件来重置，原动作仍按原请求核对。

构建摘要、具体组别、是否使用最终构建及本机原始记录索引见候选 manifest。一次检查的“通过”仅覆盖其具体场景，不等于所有客户端和长期生活完成验收。

已完成的原生业务、冷重启、农事/权限、相机及线上模型结果按组记录在 manifest；不同构建分别标注，不把早期检查冒称最新构建已重跑。双 NPC 遗迹实战 31 项、双 NPC 试炼实战 23 项为本轮较早构建的证据：两室遗迹通过真实攻击清场并原生寻路，未用管理命令清怪，第三位远处居民不获奖。0.3.4 阶段的静态/契约回归为 Java 108 项加 GPU 策略 10 项，Python 12 项，Node 26 项；本次新增检查见上文。

线上 Qwen Code 经 LiteLLM 的真实连续目标包含交付鲜花、回收铁剑、购买食物、从个人箱取入原生背包。曾 10 轮成功，但随后 14 轮复测在回收后转接其他委托，未完成购买；真实失败照实保留，不能以已执行若干动作宣称整项目标完成。关闭思考与启用思考的试验分开记录，输出预算与成本有明确上限。该测试不是长时间日程自主运行验收。

另有中间构建的入口拒绝/开放 7 项、未知传送核对与重启 11 项；这些须单独标注所属构建，不能冒称在每次最终构建上重跑。

继续阻止正式投放的项目：

1. 线上模型独立完成连续目标、处理失败和长期运行的观测，不能只凭人工逐条调用通过。
2. 全部玩家 CLI 与原生职业成长的映射；原生劳动、步行探索等任务事件不能漏记，也不能以设置工作模式替代成果。
3. 相机原生出片/照片入箱及实际取出已验证；仍需更广泛职业动作、原生合成/钓鱼/贸易事件、技能曲线与完整玩家 CLI 的统一。当前发现目录不广告未接入的能力。
4. Java、基岩与网页的实际模型、动画、气泡、菜单和操作链路；加密模型不能宣称已转换为相同的基岩/Web 外观。可暂不配置的日语音色单独记录。
5. 新居民逐个住房占用、工作范围、材料、身份/模型/人设/Scope 配置及对应验收。只在艾因格朗特初始化，允许按同一权限机制跨维度；不回灌测试世界或复制测试实体。

## 可复现回归

`standalone/tests/resident-gameplay-stage.py` 是仓库内的真实服务回归。先准备独立 Youer、当前候选及测试专用 `RecruitmentProbe`，使用测试脚本内的 `TASK_MARKET`，两个新合成居民、真实 Vortex/Vault 依赖和新数据库。AgentFriend `rpg-backend: vortex` 与 QiandengjiRpg `backend: vortex` 必须一致；否则后者会按既有双权威保护主动停用经济服务。不得移除保护来让测试通过。

环境必须带 `.resident-hybrid-qa`（内容 `SYNTHETIC_RESIDENT_HYBRID_ONLY`），游戏与 RCON 都在独立环回端口。运行前用测试夹具为两位居民准备真实库存，第一位背包 1 格是未装备铁剑、4 格可用于交付物；主手原工具保持。脚本会执行真实业务变更，因此只对这个新隔离场景运行。

```text
python paper/integrations/touhou-maids/standalone/tests/resident-gameplay-stage.py --stage <隔离服> --resident <测试UUID> --peer <另一测试UUID> --report <仓库外/gameplay.json>
```

正常停止、重新启动同一个隔离世界后，只读取原请求和原库存，不重建场景：

```text
python paper/integrations/touhou-maids/standalone/tests/resident-gameplay-stage.py --stage <原隔离服> --verify-restart <原gameplay.json> --report <仓库外/restart.json>
```
