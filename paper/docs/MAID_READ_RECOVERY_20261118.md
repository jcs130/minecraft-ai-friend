# 女仆只读观察失败不再阻塞自主循环

上线后的持续验收发现，原肥鱼的请求 `hs_794d97eaa7de4dae90095bc4` 是 `observe`，却因一次传输异常留下了非终态 `unknown`。后台按保护写操作的规则持续查询原 ID，但服务端没有为只读 context 创建动作回执，因此整个人格的后续动作被阻挡。其他两个人格未被这条记录阻挡。未证实底层这次 HTTP 异常的具体原因；已确认的是读失败会永久阻挡的恢复缺陷。

修复只修改 Python `MaidBody`：

- 只读调用失败或回包无法解析，返回明确失败，说明可以重新观察，不宣称目标已完成。
- 恢复原持久化请求时保留其动作和参数；确认是只读后，将该原 ID 结束为失败。不开新工单、不调用原动作、不修改实物。
- 写操作继续查询原回执。`brain(choice=...)` 仍是写操作，不能被当成只读；控制代次变更仍隔离该控制器。

同一测试对未修改主干先验证：10 失败、2 通过。修复后全套 Python Harness 为 143 通过、2 项原条件跳过；覆盖 HTTP 500、坏回包、观察/背包/原生任务查询、落盘后重启、重复结果读取，以及走路和切换脑的未知写保护。真实肥鱼在验收中仅查询原记录，不重复下发。

候选上线只需暂停三个 NPC 的宿主并正常退出，再替换一个 Python 模块及其摘要清单；不重启游戏服、TTS、系统一或 Graphiti。F 盘保存源码前像和停机后账本快照，回退只恢复代码，保留最新记忆、身份及动作回执。上线后必须回读上述原 ID 为 `failed`，确认原三个 UUID、原脑选择和原音色，并观察新的自主决策；候选测试不能代替该正式回读。
