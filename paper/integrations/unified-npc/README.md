# Unified server NPC host

One `agent_mc_harness.npc_service` schedules registered characters. Numen and
Touhou Little Maid supply bodies, native pathfinding, combat and real inventory;
they do not run a second language-model control loop for these bindings.

| Character | Body | Deliberate decisions |
|---|---|---|
| Kirito | Numen hosted 0.1.5, original UUID | Token Plan `qwen3.8-flash` |
| Yui | Native TLM, healer | Coding Plan `qwen3.7-plus` |
| Feiyu | Original native TLM, original companion | Token Plan `deepseek-v4.1-flash` |

The existing `agent-harness-py` runtime is the executor. Harness Hub can remain a
provider registry for other consumers; it is not another NPC controller. Models
receive current body tools with schemas, observations and memory, not shell,
arbitrary Lua, operator credentials or permission to change their own identity.
Native Lua is generated by the Numen adapter from typed actions. Existing native
combat handles each swing; a model request is not made per damage tick.

System One uses Token Plan `decision-model-preview` through `/systemone`. It
selects only from actions grounded in a fresh observation. Unavailable or stale
fast decisions fall back to the character's ordinary planner. Body denial,
server acceptance and actual task completion remain distinct receipts.

## Conversation attention

Every registered NPC receives the same `conversation.py` policy: decide who is
being addressed and whether speaking is useful before answering. Being nearby
or being the speaker's companion is insufficient. Direct questions and genuine
follow-ups are answerable; third-person mentions, other people's conversations,
group greetings, already answered questions and closing acknowledgements usually
need no reply. Important new warnings and relevant help remain possible.

The host supplies current inputs with their actual attribution, separately from
older context. Ordinary chat is not lost merely because it has low event severity.
Prompt-only real-provider tests exposed an occasional reply to somebody else's
request. System One therefore reviews a proposed reply before it is spoken. This
check does not run on every tick or gate movement, combat or healing. Both models
must choose speech; the fast model's uncalibrated confidence is recorded, not used
as an arbitrary cutoff that would suppress genuine follow-up questions.

A valid silent plan is durably recorded as listened, independently of delivered
speech. Maid inbox acknowledgement occurs once; unknown speech keeps its original
request for reconciliation. Model/transport failures do not mark inputs handled.
All future roles in this service inherit the policy. External player clients have
their own hosts and must adopt the policy separately; these files do not alter them.

Native ambient and combat voice lines remain visible and audible to nearby
players. They enter the public presentation feed separately from authored
dialogue. A canned greeting therefore cannot repeatedly wake another NPC.
The native context reports the active unified inference and conversation owner.
The old TLM selection is retained in the read-only configuration for history.

## Body activities

The original player's follow, stay and sit requests can use the same executor as
an active unified maid. They have their own original receipts and keep the
controller generation. Looking up a workshop or opening the ordinary inventory
menu keeps the lease. The owner can transfer or equip real items through the
existing inventory path while the body has no pending movement, fishing or
workshop job. The original inventory receipt and slot rules still apply. The
explicitly selected brain menu can hand off control. A fenced controller waits
for that handoff before planning again.

- For a maid role that allows `body:native:workshop` and `body:craft`, the server
  exposes the original authorized sites and recipes. The real owner must be
  present and allowed to use the containers. A completed order includes the
  original request ID, actual item and count, and which inventory changed.
  Lease changes interrupt orders that have yet to commit. An unresolved order
  blocks another host write.
- A maid role that allows `body:native:fish` can make one catch while otherwise
  guarding, with the corresponding work schedule, equipped rod, native seat
  and suitable loaded water. The registered companion must be nearby and safe.
  Receipt completion requires an original fishing event with loot. The body
  resumes guard after the catch or an interruption when the previous mode can
  be restored safely.
- A hosted Numen role that allows `body:native:nourish` eats an ordinary food
  from its own backpack when hunger is at most 14 and the observed body is idle
  and safe. Held food is consumed by the native player-body job. Completion
  carries measured item and hunger deltas.
- Maid guard selects the installed TLM attack task for the weapon. Native bow,
  crossbow, gohei and trident behavior stays with TLM. An add-on's task can
  run with an equipped item when it accepts the weapon, its own prerequisites
  pass and it accepts the target. The role's normal protection rules apply.
  A historical companion contract with no active registration stays in the
  ledger. The resident loop waits for the registration before using it.
- With `body:inventory`, a hosted Numen role sees real namespaced items and
  the hands at the time of the read. `body:equip` can use `hand: "auto"` so
  the native wardrobe chooses an eligible wearable slot. To permit a
  specific item use, add its registered ID to `native_items` and grant that
  role `body:use_item`. The item must already be in the main hand.
  This performs a short native right click. The receipt carries the original
  request ID, item count before and after and the number of changes the native
  click observed. Use the world or mod state to confirm the intended outcome.

The next plan receives recent original receipts, including work still in
progress. The dialogue journal keeps a work attempt tied to its source event
across restart so a new planning turn cannot repeat an identical order for the
same input.

### Maid starter equipment and favorability

A registered unified maid gets her starter kit on the original entity when it
first loads. An empty backpack slot receives the native 36-slot large backpack.
The ordinary totem of undying and fire and fall protection baubles go into
free native bauble slots. Existing backpacks and equipment are kept, including
an existing native extra-life bauble. A saved equipment marker prevents any
restock when an item is used, removed or the game restarts. TLM handles the
lethal effect and durability. The already configured partner respawn can still
run after a lethal hit the baubles do not stop.

The existing inventory menu displays the original favorability level and points.
Normal meals, maid beds, reading and board games use TLM's own effects and
cooldowns. At 64, 192 and 384 points, the native level increases. The host uses
the sampled level for the tone of replies to the registered partner. Other
speakers keep the role's regular tone and conversation rules apply at all levels.

The joint server candidate also includes reviewed native hosted bridge 0.1.3
from PR #307. This bridge adds Better Combat playback for accepted ordinary
melee hits on compatible observers. See the
[crossplay validation](../../probe/better-combat-crossplay/README.md).

`attention_probe.py --provider-dir <private-directory> --output <report>` tests
synthetic conversations against the configured real providers without executing
game actions. This is prompt acceptance, not proof of production crowd behaviour.

## Processes and durable state

Provision the complete `packages/agent-memory/graphiti-sidecar` HTTP dependencies,
including FastAPI and Uvicorn, as well as the selected FalkorDB driver. Before
activating a release, run `pip check`, import the HTTP entrypoint with the runtime
interpreter, and verify authenticated health plus anonymous rejection. A live
supervisor alone does not prove either child has started successfully.

Role configuration is validated against actual body verbs before any character
starts. `body:use` is invalid; use the advertised `body:use_item` only if the
current body supports it. Unsupported capabilities are not invented by the host.
Native maid arguments are derived from each server action's schema, with identity
and request routing supplied by the adapter. `guard` has no `enabled` argument.
A seated maid exposes passenger/vehicle facts and an explicit `dismount` action;
speech and inbox acknowledgement remain possible while seated. Dismounting keeps
the original body, vehicle and inventory and uses the original durable receipt.

Maid roles with `default_native_guard: true` restore guard once on a fresh idle
observation after a new lease. The check respects seating, passenger status,
manual work and a temporary wait. A fresh delegated guard does not need another
write. Native combat, follow and healing continue through quiet turns and keep
their own confirmed effects.

An existing registered companion residence can run under that native guard
delegation. It holds at most the original configured residence and a short
ticket for the original body's last confirmed generated chunk. If a body needs
rebinding, the ticket only makes that original reachable. It does not create an
entity or give the old planner control.

`supervisor.py --config <private-file>` supervises one graph sidecar and one NPC
host. An OS lock prevents duplicate supervisors/hosts; native controller leases
fence old generations. Loss of the game port or a maintenance marker pauses the
host after its current request. Numen re-admission requires a separate proof of
the exact original UUID, owner and name. It never creates replacement bodies.

Status snapshots remain atomic when readers hold an older copy on Windows. A
sharing conflict may delay the reported heartbeat until the reader closes its
handle. The managed processes continue, and sustained conflicts are logged.

The supervisor must be installed through an independent OS lifecycle. Running it
inside an interactive chat command is a test, not a persistent deployment. Store
provider keys and bootstrap material in protected private files; configuration
contains only their paths. Loopback HTTP endpoints require independent tokens.

Graphiti 0.31.2 uses a loopback FalkorDB service. Each role has a stable character
scope, local SQLite memory, immutable action journal and durable graph outbox.
Graph extraction is bounded and asynchronous; an unavailable database cannot
block combat or erase memory. Do not reset these stores during code rollback.
`import_history.py` imports the archived original maid's dialogue read-only,
including original game ticks and a separately labelled observation time. It
does not execute old tool calls or invent a wall-clock event time. Existing
native/PowerContext histories remain archived; this is not a claim that all old
external memories have already been ingested into Graphiti.

## Body migration and rollback

1. Freeze exact candidate hashes and current loaded paths. Wait for the existing
   player/activity gate, give 180/60/10-second notices, stop normally and verify
   the JVM exited. Take the current complete backup on **F only**.
2. `migrate_body.py prepare` requires the stopped game port. Check original owner,
   life, all installed worlds, item components and inventory capacity. An opaque
   backpack or duplicate original identity blocks migration. The bundle stores
   the exact entity and region preimage, player postimage and durable plan.
3. `apply` verifies those same preimages and installs only that player and one
   entity-region change. Its interrupted phase is **do not start the server**;
   reconcile the same plan. Do not create another UUID or repeat admission with
   a different identity. Remove only the migrated character from native resident
   configuration; preserve its RPG profile and historical ledgers.
4. Before enabling the host, re-admit the original identity, check current
   equipment/position/HP, native YSM selection and original RPG state. Register
   Yui once under a separately frozen UUID; no test-world entities are imported.
5. Mark admission proof only after readback. Start the single host and verify
   real dialogue, damage/healing, fast decisions and durable original receipts.

Before the new body plays, exact unchanged postimages may be reverted to the
preimage. After it plays, preserve its latest player inventory, world, RPG,
memories, authentication and action records. Pause the controller and repair or
reconcile state; never restore an old whole world or old inventory over progress.

## Compatibility boundaries

Better Combat is optional at mod load. The hosted bridge supplies charged
attacks and server upswing execution only for Numen fake players. Ordinary client
connections and attack inputs are not rewritten. Optional payloads must not eject
unmodified Java/Mineflayer clients. Native modded clients can render their own
animations; vanilla/Bedrock views are separate acceptance items.

The old classic Numen API still has a real `NumenBedrock` consumer in production.
Do not delete it simply because the new NPC executor uses hosted 0.1.5. Retire
old per-character model gateways only after verifying that no other binding
uses them. Existing TTS, camera and local System One services are separate.

## Hosted adventuring

A Numen role can opt into the server's existing guild, ruin and trial routes. Set
`adventure_partner` to the partner's actual game account. For Kirito this is
`ag_CorMy`. Add `body:native:survey`, `body:native:adventure_query` and
`body:native:adventure_action` to his existing allowed tools. Include
`body:native:nourish` for autonomous use of his own carried food.

The Numen owner can enable ordinary RPG commands for that body with
`/numen_hosted permission rules add allow command(mycli) @Kirito`. The native
permission covers the command root. The NPC host exposes only the typed actions
in the adventure catalogue. A missing rule yields a configuration receipt and
the character can still walk, eat and interact locally. The owner can remove
that specific rule to withdraw RPG access.

Real party status determines the next step. Each character accepts its own
invitation. The host queries original request IDs after an interruption.
For acceptance, check both players' rosters, their measured positions after
meeting, nearby message delivery and the combat target's health.
