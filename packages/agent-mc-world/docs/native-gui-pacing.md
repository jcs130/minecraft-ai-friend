# Ordinary native GUI pacing

`worlds.minecraft.client.syncGui` is the existing presentation enable setting (default `true`, schema `x-hot: false`; retain its client restart contract). A current managed Java camera retains its container pacing. A native viewer must bind the same action Bot through `bindNativeGuiPresentation`; the canonical autonomy viewer engine does so only after its actual listener starts. Its existing one-second publication validates confirmed player identity, viewer epoch, connection and native inventory presentation. Each pacing read checks current attachment, listener, exact client/entity identity, UUID/name, world epoch/readiness/error, native inventory availability and active viewer count. Admission expires after 1500ms without publication; epoch changes require new admission. Pacing reads never call the expensive full viewer status serializer. A saved URL or port does not enable pacing. Headless/disabled operations have zero presentation wait. Inventory-grid (2x2) pacing requires the native view; Java spectator-only operation keeps its historical exclusion.

Existing hot settings now default to click **400ms**, open **800ms**, result **1200ms**, close **600ms**, reopen gap **900ms**, operation budget **12000ms**. Explicit values, including zero, remain authoritative. Changes affect subsequent beats; disabling presentation or losing all viewers releases a current dwell within 25ms. They do not alter movement/combat/reflex timing, model scheduling or speech playback.

The six hot keys are `worlds.minecraft.show.clickMs`, `worlds.minecraft.show.dwellOpenMs`, `worlds.minecraft.show.dwellResultMs`, `worlds.minecraft.show.dwellCloseMs`, `worlds.minecraft.show.reopenGapMs` and `worlds.minecraft.show.budgetMs`. Persisted explicit values continue to override these defaults; deployment must inspect the effective settings separately.

One craft skill shares one budget across all actual `bot.craft` iterations. Known open/click/result/close beat counts distribute an insufficient budget proportionally over remaining steps, so the tail does not silently become instant. Very large operations necessarily have shorter beats under a fixed budget; `show-budget-limited` diagnostics expose the requested remaining duration, budget and spent amount. Unknown-length container operations retain the hard cap and report exhaustion. Reopen gaps remain outside this budget, as before; real native confirmation/settling time is independent of presentation time.

ShowPacer is the only presentation timer owner. Existing executor task cancellation now supplies a signal: stop, body preemption and task epoch revocation clear a pending presentation timer synchronously. End/death/respawn/window events also wake waits immediately; changed dimension/native epoch/readiness or legacy contexts without a signal are checked within 25ms. Actual window object identity is fenced before subsequent craft clicks and cleanup; numeric window IDs are insufficient. A delayed native crafting click checks ownership again at dispatch. A revoked task does not clean another window or reconstruct server slot state. Interrupted inventory-grid materials/cursor may remain until the normal confirmed reconciliation path can safely restore them.

Presentation waits never race an in-flight native click against cancellation. The original confirmation timeout, quarantine, full-snapshot recovery, native queue ownership and receipt semantics remain authoritative. A canceled operation may therefore still be draining a real unconfirmed click. No click is replayed and no unknown result becomes success.

These source tests demonstrate timing and ownership, not live icon readiness, actual browser frame cadence or audible speech speed. Last-window replay is a viewer feature and does not count as actual sequential slot presentation.
