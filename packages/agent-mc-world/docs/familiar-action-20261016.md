# Familiar actions and current-connection authorization

The public SDK exposes `prepareFastAction(toolName, arguments)` as pure recognition of caller-authorized work. A result contains semantic `steps` for a host-owned decision model and the exact `command` for dispatch. It neither invokes a model nor executes anything. Hosts must retain the original command, `action_id`, request identity, unknown outcomes and actual terminal receipts. Acceptance and a classification result are not completion.

Mineflayer-compatible short familiar step batches can include an explicit action ID. Native Java recognition is capability-gated: bounded walking navigation, observed inventory selection and view direction. Unsupported interactions, commands, scripts and combat are not silently promoted. Optional adapters preserve tool hints with the original tool definition. Native independent combat remains a separate capability.

`mc_script` accepts a shared read-only `find:{names,maxDistance,count}` recipe. It queries actual registry IDs, then one bounded search; defaults are radius8/count8, at most16 names and17 SDK calls. Backend bounds still apply (native radius16, Mineflayer32). Hidden/unloaded blocks remain unknown. Mixed body code is rejected. `ToolDef.readOnlyCall` lets hosts avoid stopping the fast lane for these recipes and API help. Inline JavaScript programs use a stable source-hash name when omitted. Explicit names keep their existing limits. Missing trace queries report the original run status/error and actual call IDs rather than inviting a guessed retry.

Native clients may expose the optional Fabric entrypoint `agent-mc-server-authorization`, a `Supplier<Map<String,Object>>` with protocol `agent-mc-server-authorization/v1`. The bundled private login owner provides allowlisted account/server/current-transport evidence only. The bridge binds it to its own generation and rejects ambiguous providers. `javaClient.requireServerAuthorization` and the native bridge setting of the same name require this evidence even when a provider is unavailable. Generic servers retain their existing behavior when authorization is not required.

Pending, revoked or blocked authorization leaves read-only evidence attached, gates new body work, and stops owned active work without replay. Host attachment retries cannot repair server authorization. Passwords stay in the configured private credential channel. Fresh configured system challenges invalidate historical success; repeated challenges while pending do not resubmit. A missing confirmation triggers bounded reconnect only for an explicitly configured reconnect account; failed credentials require intervention. These signals do not establish progress in a game objective.

Primary acceptance target: Minecraft Java1.21.1. Tests exercise the shared SES worker, real Mineflayer executor/physics fixtures, native protocol fixtures, login transport/renewal state and the Java bridge authorization evaluator. Deployment and live gameplay are verified separately by each consumer.
